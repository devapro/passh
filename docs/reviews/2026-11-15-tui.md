# Review: TUI, session, editor, print, print page (2026-11-15)

Scope: `internal/tui`, `internal/session`, `internal/editor`, `internal/print`, `internal/printweb`, production code and tests, against `docs/go-guidelines.md` and `spec.md` (§5.2, §5.5 S1/S4/S5/S6, §5.6, §6.2, §6.3, §7.2, §7.4, §13.2 tests 3 and 7).
Read-only review: nothing in the project was changed except this file.

## Summary

| Severity | Count |
|---|---|
| high | 1 |
| medium | 6 |
| low | 10 |

Top 5:

1. **TUI-001 (high)**: a lock while the rollback question is open leaves a stale "no" in the answer channel. The next unlock's rollback question is answered without the user and the TUI exits. Reproduced 20 times out of 20.
2. **TUI-002 (medium)**: `Update` does blocking I/O: the clipboard command (up to 15 s), vault saves, the lock's clipboard clear and agent stop (up to 5 s each), `printweb.Start`. The UI, the idle lock and `L` freeze meanwhile.
3. **TUI-003 (medium)**: the typed passphrase isn't wiped when the TUI quits from the lock screen, nor after `ctrl+u` or backspace in a masked input. Both proven with tests.
4. **TUI-004 (medium)**: the TUI says "Clipboard cleared." whenever no clear is pending, also when the timed clear failed; clear and agent-stop failures on exit are dropped.
5. **TUI-005 (medium)**: `edit --editor` installs its signal handlers after it has written the plaintext file, so a SIGHUP or SIGTERM in that window leaves the file on tmpfs.

What held up: S4 escaping (every rendered value in the TUI, the form and the print page traces to `sanitize` or `html/template`; no gap found), S5 masking (the constant `editor.Mask` everywhere, 10 s reveal), the print page's network, TLS, token and header rules, and the tmpfs-only editor file with wipe on every return path.
`internal/session` and `internal/print` have no finding above low.

### TUI-001: a stale answer pre-answers the next rollback question

- **Rule:** INV-1 (spec §4.10 "with a terminal, declining exits", §6.2), CONC-4. **Severity:** high. **Status:** CONFIRMED. **Effort:** S.
- **Where:** `internal/tui/model.go:132-154` (`bridge.prompt`, `bridge.answer`), `:418-424` (`cancelJob`), `:703-704` (`lock`).
- **What:** `bridge.answers` is one buffered channel shared by every job. `cancelJob` cancels the job's context and then always does `m.br.answer(false)`. The job's goroutine, parked in `prompt`, wakes on `ctx.Done()`, so the `false` stays in the channel. `prompt` never drains the channel before it asks, so the next job's question reads that `false` at once.
- **Reproduction:** the vault on disk is an older revision; `R` shows the rollback question; press `L` (or let the idle lock fire); unlock again. `vault.Open` asks the rollback question, gets the stale `false`, returns `ErrRollbackDeclined`, and `onUnlocked` quits the TUI with "stopped: this copy is older than one seen before…". The user answered nothing. A throwaway test built on `reloadRollbackHarness` (press `L`, then Enter) gave this result in 20 of 20 runs.
- **Related:** `lock` doesn't set `m.job = nil` (also confirmed), so until the cancelled reload's result arrives `onAsk` treats a late `askMsg` as live and shows the question on the lock screen for a job that no longer waits. An answer typed there (`y`) would stay in the channel the same way and pre-accept the next question. This second path needs a narrow race (the lock lands just as the reload reaches its prompt) and is SUSPECTED, not reproduced.
- **Why it matters:** the rollback question is a safety prompt; it must be answered by the user who sees it. Today's confirmed failure is in the safe direction (declines, exits), but the mechanism doesn't distinguish directions.
- **Fix:** give each job its own answer channel: create it in `startJob`, keep it in `job`, and pass it to the `prompt` closure, so an answer can only reach the job it was typed for. Drop the unconditional `answer(false)` in `cancelJob` (the cancelled context already ends the prompt), set `m.job = nil` in `lock`, and have `onAsk` ignore questions of a job other than the current one (carry `gen` in `askMsg`). Extend `TestLockDuringQuestion` to unlock again and expect the question.

### TUI-002: blocking I/O in `Update`

- **Rule:** Bubble Tea's model (commands do I/O; `Update` returns at once); CONC-1 in spirit. The guidelines have no rule for this, see "Rules" below. **Severity:** medium. **Status:** CONFIRMED by reading. **Effort:** M.
- **Where and what**, all on the UI goroutine:
  - `actions.go:322-324` `copyField`: `CopyFor` runs `clipboard.command` and waits for it, with a 15 s timeout.
  - `actions.go:454-457,633,672,719`: `Add`, `Update`, `Move`, `EditTags`, `Remove` each do a full save (§4.6: lock, hash, write, fsync, read-back decrypt, rename).
  - `model.go:708` `lockSession`: clipboard clear and agent stop, 5 s timeout together; `model.go:733` `agentRunning`: a socket round trip, 2 s timeout.
  - `actions.go:789` `startPrint`: `printweb.Start` may generate and write a certificate and binds listeners.
  - `model.go:549,560`: `v.Changed()` reads and hashes the vault file every 2 s and before each save.
- **Why it matters:** while `Update` blocks, no key is handled, the countdown stops, and the idle lock and `L` wait. A hung clipboard tool freezes the TUI for 15 s. Signals still lock (they run on their own goroutine), but the UI's copies of the data and a revealed password stay on screen until `Update` returns.
- **Fix:** move the slow calls into commands that return a result message, as `startJob` already does for unlock and reload: `copyCmd` → `copiedMsg`, `saveCmd` → `savedMsg` (mark the model busy meanwhile, which `refuse` already understands), `printStartCmd` → `printStartedMsg`, and run `Changed()` in the poll command. Keeping the lock synchronous is defensible (it must finish before the lock screen shows); say so in a comment and keep its timeout.

### TUI-003: the passphrase isn't wiped on quit, nor after `ctrl+u` or backspace

- **Rule:** SEC-1. **Severity:** medium (best effort by ADR-4, but these paths skip the wipe the code intends). **Status:** CONFIRMED with throwaway tests. **Effort:** S.
- **Where and what:**
  - `internal/tui/model.go:751-753` with `:711`: `quit` calls `m.lock(reason)`, which replaces `m.lk` with `newLockScreen()`, and only then `m.lk.pass.Wipe()`. The wipe hits the new, empty input. A passphrase typed on the lock screen and followed by `ctrl+c`, `ctrl+d` or a signal stays in memory. Test: after typing and `ctrl+c`, a copy of the input sharing the backing array still read `"hunter2-secret"`; the `esc` path read zeros.
  - `internal/editor/input.go:88-91,104-105`: `remove` shrinks the slice with `in.value[:from:from]`. After `ctrl+u` the slice has length and capacity 0, so `LineInput.Wipe` (`lineinput.go:52-55`, `clear(value[:cap])`) clears nothing: the whole passphrase survives `ctrl+u` followed by `Wipe`. After a backspace the removed last rune survives (`"…\x00t"` in the test). `LineInput.insert` already clears the old array for masked inputs; `remove` doesn't.
  - `internal/tui/model.go:385-399` `onceKey`: the passphrase bytes are zeroed only inside `VaultKey`. If the job is cancelled before the vault calls it, they aren't.
  - `internal/editor/external.go:425-429`: the edited file's bytes `b` are converted to a string and not cleared.
- **Fix:** in `quit`, wipe `m.lk.pass` before `m.lock`, or make `lock` wipe the old lock screen before it replaces it. In `lineInput.remove`, when the input is masked, `clear` the removed range (and keep the capacity so `Wipe` covers the array); simplest is to pass `masked` to `remove` or to do the clear in `LineInput.Update` around `in.key`. Give `onceKey` a `wipe` method and call it when the job ends (`onUnlocked`, and the cancelled branch of `startUnlock`). `defer clear(b)` in `EditText`.

### TUI-004: clipboard clear failures are silent or reported as success

- **Rule:** INV-6 (S6), ERR-1. **Severity:** medium. **Status:** CONFIRMED by reading. **Effort:** S–M.
- **Where and what:**
  - `internal/tui/view.go:612-615` `statusText`: when no clear is pending it prints "Clipboard cleared.". `clipboard.Pending` is also false when the timed clear ran and failed (`internal/clipboard/clipboard.go:299-304` discards `ClearNow`'s error), and `clipAdapter.CopyFor` (`tui.go:79-82`) throws away the `*clipboard.Pending` that carries the error. So a failed clear (the clipboard tool gone, the terminal closed) is announced as done.
  - `internal/tui/tui.go:280`: the `session.Report` of the exit lock is dropped, so `ClipboardErr` and `AgentErr` (the agent wasn't stopped although `session.stop_agent` is on) never reach the user. Same in the signal handler, `tui.go:259`.
  - `internal/tui/tui.go:287`: `_, _ = m.clip.clearPending(clearCtx)` has no comment and drops the last-chance clear's error.
- **Why it matters:** S6 is best effort, but the user relies on the message to know whether the password left the clipboard. The baseline already lists the same class of problem for `passh copy` (ERR-4 in `internal/cli/copy.go`).
- **Fix:** keep the `*clipboard.Pending` in `clipState` (or add `LastClearErr()` to the `Clipboard` interface) and show "Clearing the clipboard failed: …" instead of "Clipboard cleared." when it has an error. Return the exit lock's report from `Run`'s tail and print failures to the terminal after the alternate screen is left, as `waitForClear` already does for its own clear.

### TUI-005: signal handlers are installed after the plaintext file exists

- **Rule:** CONC-6, INV-2 (S1). **Severity:** medium (MUST, small window). **Status:** CONFIRMED by reading. **Effort:** S.
- **Where:** `internal/editor/external.go:364-388`: `os.MkdirTemp` (364), `writeNew` (380), then `signal.Notify` (387).
- **What:** between `writeNew` and `signal.Notify`, SIGHUP or SIGTERM has its default action. `internal/cli` installs no handler of its own for `edit` (the only `signal.Notify` there is in `printcmd.go`), so the process dies, the deferred `wipeDir` doesn't run, and the entry stays in plain text in `$XDG_RUNTIME_DIR/passh-edit-*` or `/dev/shm/passh-edit-*` until `passh doctor` reports it. It is tmpfs, not persistent disk, and the window is short.
- **Also (SUSPECTED, low):** at `:414-424` a signal that kills the editor directly (SIGHUP to the foreground process group) can make `exec.Run` return before the handler goroutine has written to `caught`; the non-blocking `select` then falls through to "the editor failed" instead of `ErrInterrupted`. The file is wiped either way; only the message and exit status differ.
- **Fix:** move the `signal.Notify`/`defer signal.Stop` block above `os.MkdirTemp`. For the second point, after `exec.Run` returns with an error, wait briefly on `caught` (or check `runCtx.Err()`) before classifying.

### TUI-006: line number parsed out of an error's text

- **Rule:** ERR-4. **Severity:** medium (MUST, low impact). **Status:** CONFIRMED. **Effort:** S (needs a small change in `internal/entrytext`).
- **Where:** `internal/editor/external.go:260` (`lineRE`), `:279-281`.
- **What:** `parseText` runs `^line (\d+): ` over `err.Error()` from `entrytext.Parse` to fill `ParseError.Line`. A wording change in `entrytext` silently gives `Line == 0`. The rule's grep doesn't catch it, because it is a regexp and not `strings.Contains`.
- **Fix:** have `entrytext.Parse` return a typed error with a `Line` field (`*entrytext.SyntaxError`), and read it with `errors.As`. The issue starts in this package; the type belongs to the other reviewer's.

### TUI-007: print page deviates from §7.4 without a logged spec change

- **Rule:** INV-1. **Severity:** medium. **Status:** CONFIRMED. **Effort:** S (a decision and two lines of documentation).
- **Where and what:**
  - `internal/printweb/net.go:167-177` `defaultSubnet`: for an address with a /32 or /128 mask (Tailscale, WireGuard) the default `allow_from` becomes the whole private range around it: `100.64.0.0/10`, `10.0.0.0/8`, `fc00::/7`. The spec says "By default that means the subnets of the bound addresses". The widening is needed (a /32's own subnet would admit nobody), but it decides who may reach the TLS listener and isn't in the spec.
  - `internal/printweb/server.go:21-27`: the spec says a second visitor "sees 'already used'"; the server stops after the first load, so a later request usually can't connect. The package comment explains it and `Result.Client` compensates.
- Neither is in `IMPLEMENTATION.md` under "Spec changes made during implementation" (it lists three other changes).
- **Fix:** report both to the owner; then either amend §7.4 and log the change, or narrow the default (for example, require an explicit `allow_from` when an address is /32).

## Rules that look wrong or impractical for this codebase

- **No rule covers the Bubble Tea model.** "No blocking in `Update`; I/O in commands; `View` is pure" is the main correctness rule of a TUI and is absent, which is how TUI-002 got in. Suggest a CONC rule with the check "every call in `Update` that touches a file, socket or process is inside a `tea.Cmd`".
- **CONC-3 (the owner waits for every goroutine)** can't be met by code that runs under Bubble Tea: commands run on goroutines the runtime owns, and `Update` must not wait. The rule should exempt goroutines that deliver a `tea.Msg` and end with their function.
- **SEC-1** reads as if a passphrase can stay in `[]byte` end to end. In the TUI each typed character arrives as `tea.KeyPressMsg.Text`, a string, and the terminal reader's buffers are out of reach. The rule should say the TUI wipes what it owns (the input widget) and that the rest is best effort.
- **DOC-2's check under-reports.** ST1022 skips grouped declarations, so `Served: …`, `ErrNoEntries: …` pass the check and break the rule (TUI-009). Either ungroup, or accept the `Name: …` form inside groups.
- **INV-5's check** ("trace each view string to a sanitize call") doesn't scale to about 60 call sites in `internal/tui`. The code already has the right tool, `inertStyled` (`view.go:698`), used only for the print dialog. Applying it to the whole frame in `View()` would make S4 structural, with the per-value calls as the first line. The rule could then name that choke point as the check.
- **API-4** says hooks are "restored with `t.Cleanup`", but `printweb` sets `allowLoopback` and `minTTL` once in `TestMain` for the whole binary, which is reasonable. The rule should allow `TestMain`.
- **gosec G118** (TOOL-4) flags `go s.run(ctx)` although the context is passed; expect a `//nolint` there.

## Structural observations

**`internal/tui` (3,859 production lines, one `app` struct with about 40 fields).** The model isn't too big to follow, but the modal state is flat: `form`, `printDlg`, `confirm`, `prompt`, `printSetup`, `help`, `search.typing`, `detail` are independent fields, and their precedence is written out separately in `mainKey` (`actions.go:91-119`), `mainPaste` (`:231-248`), `typing` (`:79-81`), `viewMain`/`fullBody` (`view.go:131-144`), `statusLines` (`:560-604`) and `footerLines` (`:629-650`). Adding a mode means touching six switches. Concrete splits:

1. **`modal` interface** (`Key`, `Paste`, `View`, `Footer`, `Typing() bool`) with one `m.modal` field; `prompt`, `confirm`, `printSetup`, the help and the hosted form and print dialog implement it. The precedence then exists once.
2. **`jobs.go`**: `job`, `bridge`, `startJob`, `cancelJob`, `onAsk`, `answerAsk` out of `model.go`, with the per-job answer channel of TUI-001. This is the only concurrent part of the model and deserves to be readable on its own.
3. **`browser`** (tree, tags, search, cursors: all of `browse.go` plus `expanded`, `tagSel`, `cur`, `search`) as a struct with its own methods; `app` keeps `entries` and hands them in. `wipe` then drops one field.
4. **Mutations as commands** (TUI-002): `saveCmd(func(Vault) error) tea.Cmd` and one `savedMsg` handler replace the five near-identical "blocked? → call → `ErrChanged`? → refresh → status" blocks at `actions.go:443-478,629-645,668-683,715-732`.
5. **`View` changes state**: `listLines` (`view.go:264-272`), `fullBodyLines` (`:394`), `viewForm` (`:676`, `SetSize`), `printDialog.frame` (`printpage.go:322`) and `rowsAndCursor` (`browse.go:258-260`) write scroll offsets and cursors while rendering. It works because the model is a pointer, but `bodyHeight` and `rowsAndCursor` are recomputed several times per frame and the offsets depend on render order. Clamp in `Update` (on key and on `WindowSizeMsg`) and keep `View` read-only.

**TUI and CLI duplication.**

- The print page dialog exists twice: `internal/tui/printpage.go` and `internal/cli/printcmd.go:426-520` (`servePrintPage`, `printPageKeys`) both list URLs, draw the QR code, show the fingerprint and countdown, copy the URL and map the result to a message. The texts already differ. A small shared type in `printweb` (the dialog's lines given a width, the countdown text) would keep them in step.
- `fmtDuration` is in `internal/tui/model.go:779` and `internal/cli/session.go:196`.
- The lipgloss styles (`styleTitle`, `styleFaint`, `styleError`, `styleWarn`) are defined in both `internal/tui/view.go:18-26` and `internal/editor/form.go:59-65`, and the "join items with ` · `, wrap between items" loop is in `tui/view.go:83-99` (`wrapItems`) and `editor/form.go:552-566` (`helpLines`). The TUI already imports `editor`; exporting them from there removes both copies.

**print and printweb.** The split is clean: `print` lays out, `printweb` and the PDF and text writers draw. Two small overlaps: the "runs of dark modules" loop for the QR code is written in `print/pdf.go:240-254` and `printweb/page.go:201-214` (a `print.QRRuns` iterator would serve both), and the row-kind-to-style mapping is spread over `pdf.go` (`height`, `draw`), `txt.go` (`txtLines`) and `page.go` (`rowClass`), so a new `RowKind` needs four edits with no compiler help; an exhaustive-switch lint or a test that walks every kind through every writer would catch a miss.

**session.** Small and well tested with an injected clock. One design note: the print page is stopped at a lock through two routes, `m.printDlg.Stop()` in `app.lock` and `sess.OnLock(dlg.Stop)` (`actions.go:807`). Both are needed today (the second covers a lock from the signal goroutine), but each started dialog adds a hook that stays until the next lock; unregistering on close, or keeping only the hook, would be tidier.
