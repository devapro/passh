### CORE-001: backup rotation keeps stale backups after a restore (high)

- Rule: INV-1 (spec §4.7: "keeps the newest `backup.keep` files"). CONFIRMED with a throwaway test.
- Where: `internal/vault/backups.go:123` (`rotate`), `:177` (`sortBackups`): order is revision first, then time.
- What's wrong: a backup is named after the revision it holds. After the vault goes back to a lower revision (restoring a backup as §4.7 describes, or an older copy from a USB stick or another machine), every new backup has a lower revision than the pre-restore ones and sorts last. `rotate` then removes it on the next save; only the backup just written is protected.
- Proof (`keep = 3`, vault at r12 with backups r9–r11, then an r2 copy restored and four saves made):

  ```
  after save 4 (vault r 6):
     12:34 r 11     <- stale, pre-restore
     12:31 r 10     <- stale
     12:28 r 9      <- stale
     12:47 r 5      <- the only backup of the new work
  ```

  The backups of r2, r3 and r4 were each deleted one save after they were made.
- Why it matters: until the revision passes the old maximum, the undo depth is 1 instead of `backup.keep`, the folder holds `keep + 1` files, and `passh backups` ("newest first") lists the stale files on top. The user gets no warning. The comment explains the choice (a clock that went back), but the deviation from §4.7 isn't in `IMPLEMENTATION.md`.
- Fix: order by the time in the file name, then revision, then sequence, for both rotation and listing. To stay safe against a clock that jumped back, never remove a backup newer in name-time order than the one just written, or keep the newest `keep` by directory order of creation (mtime as a tie-breaker). Add a regression test for "restore an older copy, save N times". If revision order is intended, report it as a spec change.
- Effort: S.

### CORE-002: a `Close` error after the vault was replaced turns a finished save into a failure (medium)

- Rules: ERR-1, FILE-3, INV-11 (§4.6 "leaves either the old file or the new one"). CONFIRMED by reading; not reproduced, because it needs `close(2)` to fail.
- Where: `internal/vault/vault.go:659` and `:689` (`return t.close()` in `replace`), called from `commit` at `:612`.
- What's wrong: by the time `t.close()` runs, the new file is the vault (the rename or exchange succeeded and the temp file was fsynced earlier). If `Close` fails, `commit` returns the error with `installed == false`: the in-memory `sum`, `data` and `keyBlock` aren't updated, the rollback record isn't written, and the folder isn't fsynced. The caller is told the save failed, the next save fails with `ErrChanged`, and after `Passwd`/`Rekey` the `Vault` still holds the old key block and key although the file has the new ones.
- The same call is handled the opposite way in three places, where the error is dropped without `_ =` or a comment (errcheck): `vault.go:440` (`create`), `fs.go:290` (`writeAtomic`), `backups.go:110`.
- Two related paths in `replace`:
  - `vault.go:672` and `:677`: when `keepAside` can't rename the file, it returns `t.path`, the error message says the other version "is kept in" that path, and then the deferred `t.discard()` in `commit` (`:581`) removes it. Needs three faults at once, but the message is then wrong and the file is lost.
  - `vault.go:682`–`685`: when the exchanged-out file can't be read (anything but "not exist"), it is removed after a warning, although it wasn't checked against the opened file.
- Fix: treat `close` after a successful rename as best effort everywhere: `_ = t.close() // already fsynced and renamed; nothing to undo`, or pass the error to `v.warn`. In `replace`, set a flag on `t` (or return a "keep" result) so `commit` doesn't discard a path that `keepAside` reported, and move an unverifiable exchanged-out file aside with `keepAside` instead of removing it.
- Effort: S.

### CORE-003: saves can't be cancelled; lock waits poll for up to 15 s (medium)

- Rule: CONC-1 (MUST). CONFIRMED by reading.
- Where: `internal/vault/fs.go:350` (`lockFile`: `time.Sleep(lockPoll)` until `lockWait`, 15 s); used for the save lock, the backups lock (`backups.go:85`) and the rollback record lock (`rollback.go:84`), so one save can wait three times. `Create`, `Passwd`, `Rekey` (scrypt at 2^18, several seconds on a Pi) and `Add`/`Update`/`Move`/`Remove`/`EditTags`/`Apply` take no `ctx`; only `Open` and `Reload` do.
- Why it matters: in the TUI, where signals are caught, a save behind another passh's lock freezes the screen for up to 15 s and ignores Ctrl-C, SIGHUP and the idle lock (§5.2).
- Note: spec §10.3 gives `Put`, `Move` and `Remove` without a context, so the signatures follow the spec. Cancelling between the rename and the folder fsync would also be wrong.
- Fix: either pass a context only to the waiting parts (`lockFile(ctx, …)` selecting on `ctx.Done()` and a timer; check `ctx.Err()` before scrypt and before step 3), or record the decision as `// exception CONC-1: §10.3 signatures; a save is short and must not stop half-way` at `mutate` and `lockFile`.
- Effort: M (API change through `cli` and `tui`), S for the exception comment.

### CORE-004: fixed sleeps used as synchronisation in tests (medium)

- Rule: TEST-7 (MUST). CONFIRMED by reading; the baseline already lists it as open.
- Where, `test/acceptance` (43 `time.Sleep` calls): about 26 are polling loops or let time pass for a TTL under test, which the rule allows (most lack the required comment). About 17 are fixed "let it settle" waits:
  - `harness_test.go:514`, `:595`, `:633` (20 ms "to switch the terminal mode" before typing; every `answer` goes through `:514`);
  - `agent_export_test.go:188`, `:227`, `:255`, `:336`, `:341`, `:384`, `:402`, `:457`;
  - `copy_test.go:113`, `crash_test.go:195`, `editor_test.go:146`, `paperkey_test.go:157`, `safety_disk_test.go:402`, `tamper_test.go:382`.
- Where, unit tests: `internal/vault/save_test.go:299` sleeps 150 ms and then asserts that the save is still waiting. It can't flake into a failure, but on a slow machine it can pass without having tested anything.
- Why it matters: on a loaded machine 20 ms isn't enough for the child to reach raw mode, so typed input is echoed and screen assertions can fail or pass for the wrong reason.
- Fix: in `answer`, wait for an observable state instead of a time: poll the pty's termios until `ECHO` is off (`unix.IoctlGetTermios` on the master) for passphrase prompts; for the others wait for the prompt text, which the harness already does. In `save_test.go`, use the `hookLocked` test hook or a short `lockPoll` counter to know the save is waiting. Add the "time passing under test" comment to the TTL sleeps.
- Effort: M.

### CORE-005: test hooks are reset inline, not with `t.Cleanup` (medium)

- Rules: API-4 ("restored with `t.Cleanup`"), TEST-13. CONFIRMED by reading.
- Where: `internal/vault/hardening_test.go:78`–`84`, `:127`–`133`, `:173`–`183`, `:533`–`541`; `plaintext_test.go:94`–`102`; `save_test.go:372`–`379`; `internal/config/agentdir_test.go:242`–`244` (`getuid`).
- What's wrong: the pattern is `testHook = func…; call; testHook = nil`. Several hooks call helpers that can `t.Fatal` (`putInPlace(t, …)` at `hardening_test.go:80` and `:129`). `t.Fatal` inside the hook unwinds the save and skips the reset, so the hook stays set for every later test in the package, including the four `t.Parallel` tests in `passphrase_test.go`, which run last. One failure then shows up as several unrelated ones.
- Fix: one helper, used everywhere:

  ```go
  func setHook(t *testing.T, fn func(point, file string)) {
      t.Helper()
      testHook = fn
      t.Cleanup(func() { testHook = nil })
  }
  ```

  Same for `getuid` in `agentdir_test.go`. `noExchange` already does it this way.
- Effort: S.

## Rules that look wrong or impractical for this codebase

- **CONC-1 against spec §10.3.** The spec's `Vault` interface has no context on `Put`, `Move` and `Remove`, and INV-1 says the spec wins. The rule should say which vault operations are exempt, or name the parts that must honour a context (lock waits, scrypt), so CORE-003 has a clear target.
- **ERR-3 "tests included".** `err != locked` in `damage_test.go:179` and `err != boom` in `vault_test.go:189` check that an error passes through unwrapped, which `errors.Is` can't express. Allow identity comparison in tests where the test is about identity, with a `//nolint:errorlint // asserts the error is not wrapped`.
- **API-6 "explicit field tags".** `internal/model` writes the vault JSON with hand-written marshalers and literal key strings, not struct tags, to keep unknown keys and key order. That meets the rule's intent; the wording should accept "tags or explicit key names in a custom marshaler".
- **ERR-5 "no newline".** `vault.OpenError.Error()` and `config.Error.Error()` are multi-line on purpose (the backup list of §4.5; several config problems). The rule should allow a multi-line error where the spec asks for a list, and say that such errors are printed with `sanitize.Text`.
- **DOC-2's check doesn't catch DOC-2's own example.** ST1020–ST1022 accept `ErrX: …`, so the "not `ErrDisabled: …`" form can only be found by grep. Add `grep -rnE '^\s*// Err[A-Za-z]+:' --include='*.go' internal`, or drop that part of the rule.
- **API-4's hook list is incomplete.** The check command doesn't list `lockWait`, `lockPoll` and `renameNoReplaceFn` (`internal/vault/fs.go:306`, `:341`), which tests change.
- **INV-10 "keeps age's maximum work factor check".** age's default maximum is 2^22 (`scrypt.go:129`), which is 4 GiB of memory. passh only ever writes 2^18, so a tampered key block can make each passphrase attempt cost 16 times the memory and time before it fails; on a 1 GiB Pi that is an out-of-memory kill. Consider requiring `SetMaxWorkFactor(20)` or so in `keys.UnwrapKey`, with a message that says the key block asks for too much work.
- **Baseline, last bullet.** `go.mod` no longer marks every requirement `// indirect`: the direct block is separate and correct. The bullet can go.

## Resolution (2026-11-15)

Core packages (`vault`, `keys`, `vaultfile`, `model`, `paths`, `config`, `gen`, `sanitize`, `harden`). Exported API changed only by additions. Gates: gofmt, `go vet` (linux, darwin), staticcheck and golangci-lint clean on these packages; `go test -race` and `-shuffle=on -count=2` pass.

- **CORE-001 (fixed):** backups are named `<seq>-<UTC time>-r<revision>.passh` (`00000042-20261115T120031Z-r41.passh`; seq zero-padded to 8 digits, one more than the highest in the folder, assigned under the backups lock). Rotation and listing order by seq only, newest first; old names (`<time>-r<rev>[-n].passh`) count as older than every numbered one, ordered among themselves by time, revision, suffix. Tests: `TestBackupsAfterRestore` (restore then four saves), `TestRotationClockSkew`, `TestBackupsOldNames`, `TestBackupNames`. Spec §4.7 needs the new name.
- **CORE-002 (fixed):** after the rename, `closeInstalled` turns a close error into a warning (commit and create) and in-memory state is always updated; `writeBackup`/`writeAtomic` discard it explicitly with a reason. `keepAside` sets `tempFile.kept` when it can't move the other version, so `discard` keeps it, and the error names its temporary path; an exchanged-out file that can't be read is kept aside, not removed. Tests: `TestCloseErrorAfterRename`, `TestReplacedAndKeepAsideFails`, `TestReplacedFileUnreadable`.
- **CORE-003 part 1 (fixed):** `lockFile(ctx, …)` waits on timers in a `select` with `ctx.Done()`; context reaches the save, backups and record locks, is checked before scrypt and before step 3, and never stops a save after its rename.
