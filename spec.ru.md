## 1. Краткое описание

passh — это один бинарный файл на Go для управления паролями, которые хранятся в **одном зашифрованном файле**. Вы устанавливаете один файл, запускаете `passh init` и затем запускаете `passh`, как любую другую команду. Он работает там, где лежит файл хранилища: на ноутбуке или на сервере, к которому вы подключаетесь обычным `ssh`. Никакие другие программы не нужны: ни GnuPG, ни git.

Файл хранилища:

- это один текстовый файл, который можно скопировать куда угодно любым способом и проверить после копирования;
- открывается одной парольной фразой, а если вы её забыли — бумажным ключом восстановления;
- шифрует всё, включая имена записей и теги;
- открывается стандартной утилитой `age`, если passh когда-нибудь станет недоступен.

passh предлагает:

- TUI для просмотра по папкам (категориям) и тегам;
- копирование в буфер обмена, в том числе по SSH (OSC 52), с очисткой по тайм-ауту;
- блокировку после периода бездействия и агент, который держит хранилище разблокированным ограниченное время для скриптов и SSH;
- односторонний импорт из хранилища `pass`;
- экспорт (CSV / JSON / Bitwarden JSON) и печать (текстовый лист, а также одноразовая страница печати, которая открывается в браузере в LAN или VPN).

## 2. Цели и что не входит в цели

### Цели

| # | Цель |
|---|------|
| G1 | Один статический бинарный файл на Go для `linux/amd64`, `linux/arm64`, `linux/arm/v7`, `darwin/amd64` и `darwin/arm64` |
| G2 | Вся установка: скопировать бинарный файл и запустить `passh init`. Без root, без других программ, без изменений в системе (§3.2) |
| G3 | Переносимое хранилище: один файл, который переживает любой способ копирования, проверяется после копирования и открывается на любой машине парольной фразой или бумажным ключом восстановления, даже без passh (§4.8, §8) |
| G4 | Одинаковая работа локально и по SSH |
| G5 | Просмотр и поиск по папкам и по тегам в TUI |
| G6 | Экспорт и печать для миграции и бумажной резервной копии, включая печать из браузера без сохранения файла |
| G7 | Односторонняя миграция из `pass` |

### Что не входит в цели (v1)

- Расширения для браузеров, автозаполнение на мобильных устройствах, нативные мобильные приложения
- Совместный доступ нескольких пользователей, роли, права для отдельных устройств
- Веб-интерфейс или HTTP API. Единственное исключение — одноразовая страница печати (§7.4)
- Режим сервера, системные службы, настройка SSH, контейнеры
- Совместимость с `pass` сверх одностороннего импорта
- Слияние копий хранилища, которые редактировались на разных машинах: запланировано на v1.1 (§4.11)
- TOTP (запланирован на v1.1); импорт из других менеджеров паролей
- Защита от атакующего, который контролирует вашу учётную запись
- Windows

## 3. Установка и настройка

### 3.1 Установка

Скопируйте бинарный файл `passh` в папку из вашего `PATH`, например в `~/.local/bin`, и запустите `passh init` (§5.4).

У passh нет зависимостей во время выполнения. `gpg` нужен только для однократного `passh import pass` (§4.9).

### 3.2 След в системе

passh **не меняет систему**. Он пишет только в эти места:

| Путь | Что passh туда пишет |
|---|---|
| Файл хранилища (`vault` в конфигурации; `passh init` по умолчанию создаёт `$XDG_DATA_HOME/passh/vault.passh`, а если переменная не задана — `~/.local/share/passh/vault.passh`) | Хранилище. Во время сохранения — временный файл `.<name>.tmp-<random>` в той же папке (§4.6). В редких случаях — файл конфликта `<base>.conflict-<stamp>[-N].passh` рядом с хранилищем: другая версия, если другая программа заменила хранилище во время последнего переименования при сохранении (§4.6) |
| Конфигурационный файл (§3.3) | Создаётся командой `passh init`, только если его нет; после этого никогда не перезаписывается |
| `$XDG_STATE_HOME/passh/` (по умолчанию `~/.local/state/passh/`) | Автоматические резервные копии (§4.7), файлы блокировки, наибольшая ревизия, замеченная для каждого хранилища (§4.10), сокет агента в `agent/` (§5.3), сертификат и ключ страницы печати (§7.4) |
| `passh-<uid>/` в `$TMPDIR` или `/tmp`, только если путь в папке состояния слишком длинный для сокета | Сокет агента (§5.3) |
| Временная папка на tmpfs | Только для `edit --editor` (§5.6); после использования удаляется |

passh никогда:

- не требует root;
- не пишет в системные файлы и в файлы других пользователей;
- не меняет файлы запуска shell и настройки других программ (gpg, git, ssh);
- не устанавливает службы и задания cron;
- не трогает настройки брандмауэра, swap и SSH;
- ничего не устанавливает в хранилища сертификатов ОС или браузера.

**Фоновые процессы:** единственный процесс, который продолжает работать после завершения команды, — агент, и только после явного `passh unlock`. Он завершается сам после `agent.idle_ttl` без обращений или `agent.max_ttl` в общей сложности, а также по `passh lock` (§5.3). Сервер страницы печати работает внутри процесса passh.

**Удаление:** удалите бинарный файл, конфигурационный файл и `~/.local/state/passh/` (там лежат автоматические резервные копии; их можно оставить). Файл хранилища остаётся на месте.

Все пути, имена и права: [storage.md §1](docs/spec/storage.md#1-folders-and-files-32).

### 3.3 Конфигурационный файл

Расположение (используется первый найденный вариант):

1. `--config <file>`;
2. `$PASSH_CONFIG`;
3. `$XDG_CONFIG_HOME/passh/config.toml` (по умолчанию `~/.config/passh/config.toml`).

Обязателен только `vault`; его записывает `passh init`:

```toml
vault    = "~/.local/share/passh/vault.passh"
language = "en"         # en, ru или sr (сербский, латиница)

[session]
idle_ttl   = "5m"       # TUI locks after this much inactivity
stop_agent = true       # a TUI lock also stops the agent (§5.3)

[agent]                 # started only by `passh unlock` (§5.3)
idle_ttl = "15m"        # exits after this long without a request
max_ttl  = "2h"         # and after this long in any case

[backup]
keep = 10               # previous versions kept in ~/.local/state/passh/backups/ (0 = off)

[rollback]
warn = true             # warn when a vault is older than one seen before (§4.10)

[clipboard]
clear_after = "30s"
osc52       = true      # copy through the terminal (works over SSH)
command     = []        # optional local tool instead, e.g. ["pbcopy"] or ["wl-copy"]

[print_web]             # §7.4; off unless enabled
enabled    = false
port       = 8443
interfaces = ["wg0", "eth0"]
allow_from = []         # extra CIDR limit; default = subnets of the bound addresses
hostnames  = []         # optional names for the certificate, e.g. ["pi.local"]
ttl        = "5m"       # 1–15 min
```

- `--vault <file>` переопределяет `vault` для одной команды. С `--vault` passh работает и без конфигурационного файла.
- Если конфигурационного файла нет, passh выводит подсказку, как его создать (`passh init`).
- Неизвестные ключи считаются ошибкой, чтобы опечатки не оставались незамеченными.
- Непустой `print_web.allow_from` **заменяет** значение по умолчанию (подсети адресов привязки), а не ограничивает его дополнительно, что бы ни говорил комментарий выше (§7.4; открытый вопрос в §14).
- `language` задаёт язык всего, что passh пишет для людей: сообщений, запросов, ошибок, `--help`, TUI, текстового листа, листа ключа восстановления и страницы печати (включая CONFIDENTIAL), а также отчётов для людей на stdout: `doctor`, отчёта `import pass` и пояснения в строке `rollback` у `verify --full`. По умолчанию `en`; `ru` — русский, `sr` — сербский латиницей; любое другое значение — ошибка. То, что читают скрипты или сам passh, одинаково на всех языках: данные на stdout (`ls`, `find`, `tags`, `show`, `export`, …), имена команд, флагов, полей и ключей конфига, а также фразы, которые набирают для подтверждения (`PRINT RECOVERY KEY`, `EXPORT PLAINTEXT`, `PRINT`). Текст ошибок операционной системы или библиотек может остаться английским. Если конфигурационный файл не загружается (только `--vault`, до `passh init` или файл есть, но в нём ошибка), passh говорит по-английски. Побайтное совпадение вывода требуется только для английского: для `ru` и `sr` спецификация задаёт, что переводится и что нет, правила множественного числа, ответы «да/нет», термины глоссария и фиксированные строки, перечисленные в приложениях (например, рамку листов), но не формулировки остальных сообщений.

Точный разбор, значения по умолчанию и сообщения: [storage.md §2](docs/spec/storage.md#2-config-file-33); языки: [i18n.md](docs/spec/i18n.md).

## 4. Хранение

### 4.1 Файл хранилища

Хранилище — один текстовый файл (на практике ASCII) с правами 0600. Расположение по умолчанию (`passh init`): `$XDG_DATA_HOME/passh/vault.passh`, а если переменная не задана — `~/.local/share/passh/vault.passh`. Формат на уровне байтов: [vault-format.md](docs/spec/vault-format.md).

```
passh-vault 1
-----BEGIN AGE ENCRYPTED FILE-----
(key block: the vault key, encrypted with the passphrase)
-----END AGE ENCRYPTED FILE-----
-----BEGIN AGE ENCRYPTED FILE-----
(data block: all entries as JSON, encrypted to the vault key)
-----END AGE ENCRYPTED FILE-----
```

- **Строка 1** — сигнатура и версия контейнера.
- **Блок ключа:** файл age, зашифрованный парольной фразой (получатель scrypt из age с коэффициентом сложности 2^18 — значение age по умолчанию; облегчённой настройки нет, даже для слабых устройств; блок ключа, запрашивающий больший коэффициент, отклоняется до запуска scrypt, чтобы подделанный файл не исчерпал память слабого устройства). Его открытый текст — **ключ хранилища**: случайная идентичность age X25519 (`AGE-SECRET-KEY-1…`) в одной строке, то есть корректный файл идентичности age.
- **Блок данных:** файл age, зашифрованный на ключ хранилища. Его открытый текст — JSON из §4.2.
- Оба блока записаны в ASCII-броне age (base64, 64 столбца), поэтому файл — обычный текст, и стандартная утилита `age` читает каждый блок (§8).
- **Открытая половина ключа хранилища (получатель `age1…`) нигде не записывается** (S9). age не подтверждает, кто зашифровал файл: любой, кто знает получателя, мог бы собрать блок данных, который расшифруется. Пока получатель остаётся секретным, корректный блок данных может создать только владелец ключа хранилища.
- Снаружи видны только имя и размер файла.

### 4.2 Формат данных

Открытый текст блока данных:

```json
{
  "format": "passh-vault-data",
  "version": 1,
  "vault_id": "0f6c1d2e-…",
  "revision": 42,
  "saved_at": "2026-11-15T12:00:00Z",
  "entries": [
    {
      "id": "8d1e7a90-…",
      "path": "work/github",
      "password": "s3cr3t-P@ss",
      "username": "arsenii",
      "url": "https://github.com",
      "tags": ["work", "dev", "2fa"],
      "fields": [ { "key": "recovery-email", "value": "me@example.com" } ],
      "notes": "Free-form notes. Recovery codes, etc.",
      "created_at": "2026-11-01T09:00:00Z",
      "updated_at": "2026-11-15T12:00:00Z"
    }
  ],
  "deleted": [
    { "id": "3b9f…", "deleted_at": "2026-11-10T18:30:00Z" }
  ]
}
```

- `vault_id` — случайное значение, которое задаёт `init` и которое никогда не меняется, даже при `rekey`. `revision` увеличивается на 1 при каждом сохранении.
- У каждой записи есть случайный `id`, который не меняется при редактировании и перемещении, а также `created_at` и `updated_at`.
- `fields` хранит остальные пары `key: value` упорядоченным списком; ключи могут повторяться. `otp` зарезервирован для TOTP (v1.1); его значения и значения `otpauth://` маскируются так же, как пароли.
- `deleted` хранит надгробие (только `id` и время, без данных) для каждой удалённой записи, чтобы `passh merge` мог отличить «удалено здесь» от «добавлено там» (§4.11).
- Неизвестные ключи на любом уровне сохраняются при записи, поэтому старая версия passh не теряет то, что записала новая. `version` выше известной passh отклоняется с сообщением «made by a newer passh».
- Данные проверяются при каждом открытии и перед каждым сохранением. `password`, `username`, `url` и значения полей — однострочные; теги нормализуются в NFC, обрезаются по краям и не повторяются (§4.4); ни одно дополнительное поле не называется `username`, `url` или `tags` (в любом регистре). Данные, нарушающие правило, некорректны («data is damaged», §4.5). Более новая версия passh, которая ослабит правило (многострочные значения, меньше зарезервированных ключей, новые типы значений), ДОЛЖНА (MUST) повысить `version` данных, чтобы эта версия отклоняла такие данные как более новые, а не сообщала о повреждении.
- Открытие и чтение никогда не перезаписывают файл. Сохраняют его только изменения (§4.6).

Схема, проверка, сериализация и то, как каждая операция меняет данные: [vault-format.md §4](docs/spec/vault-format.md#4-data-42).

### 4.3 Текстовая форма записи

`show`, `show --raw`, `edit --editor` и `import pass` используют привычную текстовую форму в стиле pass:

```
s3cr3t-P@ss
username: arsenii
url: https://github.com
tags: work, dev, 2fa
recovery-email: me@example.com
---
Free-form notes. Recovery codes, etc.
```

- Строка 1 — пароль, за ней идут метаданные `key: value`, затем произвольные заметки.
- Метаданные заканчиваются на строке `---` или на первой строке, которая не подходит под формат `key: value`. Всё, что идёт дальше, — заметки.
- `username`, `url` и `tags` соответствуют одноимённым полям JSON; остальные ключи попадают в `fields` в исходном порядке.

Точная грамматика записи и чтения: [vault-format.md §5](docs/spec/vault-format.md#5-entry-text-form-43).

### 4.4 Пути, папки и теги

- `path` записи имеет вид `folder/…/name`. **Папки = категории**, как в pass. Папка существует, пока в ней есть записи.
- Каждый путь, полученный от пользователя или при импорте, проходит через один валидатор:
  - сегменты разделяются `/`, ни один не пустой, в начале и в конце нет `/`;
  - нет сегментов `.` или `..`, и ни один сегмент не начинается с `-`;
  - нет управляющих символов; Unicode нормализуется в NFC; не больше 1024 байт.
- Пути уникальны и чувствительны к регистру.
- Теги хранятся в самих записях. После разблокировки всё хранилище находится в памяти, поэтому для вывода списка по тегу индекс не нужен.
- Теги нормализуются в NFC и обрезаются по краям, не бывают пустыми и не содержат запятых и управляющих символов; повторяющиеся теги записи отбрасываются, остаётся первый.

Правила валидатора и сообщения, смысл папок и порядок сортировки: [vault-format.md §6](docs/spec/vault-format.md#6-paths-and-folders-44).

### 4.5 Открытие

passh снисходителен к «обёртке» файла и строг к его содержимому. Копия, прошедшая через почту, текстовый редактор или другую ОС, всё равно открывается; повреждённая копия никогда не открывается частично.

**Снисходительность.** Перед разбором passh:

- принимает окончания строк LF, CRLF и CR и UTF-8 BOM, а также обрезает пробелы вокруг строк;
- склеивает base64 каждого блока независимо от длины строк, потому что почтовые клиенты и редакторы переносят строки;
- игнорирует текст до строки `passh-vault` и после последней строки `END`, выводя предупреждение.

**Строгость.** passh отклоняет файл и объясняет причину:

| Проблема | Сообщение |
|---|---|
| Нет строки `passh-vault` | not a passh vault |
| `version` контейнера или данных выше известной | made by a newer passh; upgrade passh |
| Файл кончается раньше времени: он пустой, обрывается внутри строки `passh-vault` или до блока либо его строки `END` | file is truncated |
| Неверный base64 или заголовок age, отсутствующая или повреждённая строка `BEGIN` либо строка `END`, которой нет перед следующей строкой `BEGIN` | file is damaged (block 1 or 2) |
| Блок ключа не расшифровывается | wrong passphrase, or the key block is damaged |
| Блок данных не расшифровывается или не является корректным JSON | data is damaged; restore a backup (со списком копий, §4.7) |

age проверяет подлинность каждого байта каждого блока и обнаруживает обрезку, поэтому о повреждении всегда сообщается, и passh никогда не показывает данные частично.

Через агента (§5.3) блок ключа, отличающийся от разблокированного, нельзя отличить от `passwd`, сделанного в другом месте, поэтому passh запрашивает парольную фразу, а без терминала сообщает, что хранилище заблокировано. Если блок данных не расшифровывается ключом агента, это сообщается как повреждение данных.

passh всегда записывает каноническую форму: окончания строк LF, строки по 64 столбца, ничего вокруг блоков.

Разбор по шагам, все сообщения и проверки без ключа: [vault-format.md §2](docs/spec/vault-format.md#2-container-41-45).

### 4.6 Сохранение

Каждое изменение (добавление, редактирование, перемещение, удаление, теги, `passwd`, `rekey`, `recover`, импорт) сохраняется сразу как одна новая ревизия:

1. Взять исключительную блокировку (`flock`) в `~/.local/state/passh/locks/` по реальному пути хранилища, чтобы два процесса passh на машине не сохраняли одновременно. Удалить временные файлы, оставшиеся от прерванных сохранений.
2. Снова прочитать файл хранилища и сравнить его SHA-256 с тем, что был записан при открытии. Если они различаются, файл изменил другой процесс, инструмент синхронизации или ручное копирование. Тогда passh не сохраняет: он сообщает об этом и сохраняет ваш ввод (форма в TUI сохраняет значения), чтобы вы могли перезагрузить хранилище и повторить изменение.
3. Сериализовать данные с `revision` + 1 и зашифровать блок данных на ключ хранилища. Блок ключа копируется байт в байт, кроме случаев `passwd`, `rekey` и `recover`.
4. Записать временный файл `.<name>.tmp-<random>` в папку хранилища с правами 0600 и выполнить для него `fsync`.
5. Прочитать временный файл обратно, разобрать его, расшифровать блок данных и сравнить с тем, что было записано. При любом расхождении удалить временный файл и завершиться ошибкой; хранилище остаётся без изменений.
6. Скопировать текущий файл хранилища в автоматические резервные копии (§4.7).
7. Выполнить `rename` временного файла поверх хранилища (атомарно в пределах одной файловой системы), затем `fsync` папки.

- Сохранение, прерванное в любой момент (сбой, отключение питания, `kill -9`), оставляет либо старый файл, либо новый, причём каждый целиком.
- Если путь к хранилищу — символическая ссылка, passh пишет в её цель и сохраняет ссылку.
- Если другая программа заменит хранилище между шагом 6 и `rename`, passh замечает это там, где файловая система поддерживает атомарный обмен (тогда `rename` на шаге 7 — это обмен): он возвращает ту версию на место и сообщает об изменении, как на шаге 2. Если вернуть её не удаётся, он сохраняет её рядом с хранилищем как `<base>.conflict-<stamp>[-N].passh` и называет этот файл.

Блокировки, каждый шаг с его сообщениями, обмен и запасные варианты для файловых систем без него: [storage.md §4](docs/spec/storage.md#4-saving-46).

### 4.7 Автоматические резервные копии

- Перед каждым сохранением passh копирует текущий файл хранилища в `~/.local/state/passh/backups/<vault_id>/<seq>-<UTC time>-r<revision>.passh` и хранит `backup.keep` файлов, сделанных последними (по умолчанию 10; 0 отключает копии). `<seq>` — счётчик: наибольший номер в папке + 1; больше он нигде не хранится и записывается минимум восемью цифрами (больше, когда номер вырастет). Только он задаёт порядок, поэтому неверные часы или восстановленная старая ревизия никогда не заставят passh удалить самые новые копии.
- Каждая резервная копия — полноценное хранилище. Она открывается командой `passh --vault <file>` с парольной фразой или бумажным ключом, которые были действительны на момент её создания. Сохранение в файл из папки резервных копий отклоняется: сначала скопируйте его оттуда.
- `passh backups` выводит их список со временем и ревизией. Чтобы вернуться к одной из них, скопируйте её поверх файла хранилища и выполните `passh verify --full`.
- Эти копии позволяют отменить ошибки на этой машине. От потери диска они не защищают, поэтому храните копию где-то ещё (§4.8, §8).

Имена папок и файлов, запись, ротация и вывод `backups`: [storage.md §5](docs/spec/storage.md#5-automatic-backups-47).

### 4.8 Копирование и проверка

Хранилище рассчитано на копирование:

- **Самодостаточность:** нужны только файл и парольная фраза (или бумажный ключ). Нет файлов ключей, ссылок на другие файлы и ничего, что привязано к машине, ОС или процессору.
- **Любой канал:** `cp`, `scp`, `rsync`, флешка (FAT32 и exFAT подходят), облачная папка, вложение в письмо или текст, вставленный в заметку (§4.5).
- **Проверка:** повреждение и обрезка всегда обнаруживаются (§4.5).

Команды:

- `passh backup <dest>` копирует хранилище в файл или папку (имя по умолчанию `<name>-<UTC time>.passh`), выполняет `fsync`, читает копию обратно и сравнивает её с байтами, которые собирался записать. Копия пишется во временный файл рядом с целевым и переименовывается на место только после проверки, поэтому прерванное копирование никогда не оставляет неполный файл под итоговым именем; существующий файл не перезаписывается. Эти байты — байты файла хранилища, поэтому у копии тот же SHA-256, что у хранилища; хранилище не в канонической форме (§4.5) копируется вместо этого в виде канонической перекодировки, и её SHA-256 отличается от SHA-256 хранилища (passh об этом сообщает). Парольная фраза не нужна.
- `passh verify [file]` проверяет копию без парольной фразы: строку `passh-vault`, целостность обоих блоков, корректность base64 и заголовков age. Выводит SHA-256 и размер файла; у побайтно точной копии SHA-256 совпадает с оригиналом.
- `passh verify --full [file]` дополнительно расшифровывает копию (через агент или запросив парольную фразу) и проверяет данные. Выводит `vault_id`, `revision`, `saved_at` и количество записей.

Вывод и сообщения `backup` и `verify`: [storage.md §6](docs/spec/storage.md#6-copying-and-verifying-48).

### 4.9 Импорт из pass

```
passh import pass [dir] [--overwrite] [--dry-run]
```

- По умолчанию `dir` — это `$PASSWORD_STORE_DIR`, затем `~/.password-store`. Хранилище pass только читается и никогда не меняется.
- passh обходит файлы `*.gpg` через `os.Root`, поэтому символические ссылки не могут вести за пределы хранилища. Он пропускает `.git`, `.gpg-id` и другие файлы и папки, начинающиеся с точки.
- Каждый файл расшифровывается командой `gpg --decrypt` с вашими gpg-agent и pinentry, как это делает `pass` (с заданным `GPG_TTY`). gpg нужен только для этой команды. Открытый текст приходит через канал (pipe) и остаётся в памяти.
- Каждая запись разбирается как текст (§4.3). `username:`, `user:` и `login:` становятся `username`; строки `otpauth://` попадают в поле `otp`; остальные ключи — в `fields`.
- Путь — это путь к файлу без `.gpg`. Пути, не прошедшие валидатор (§4.4), пропускаются, и о них сообщается.
- Пути, которые уже есть в хранилище, пропускаются и перечисляются, если не указан `--overwrite`.
- `--dry-run` выводит, что будет импортировано, и список конфликтов, ничего не расшифровывая.
- Весь импорт — одно сохранение (§4.6). В конце passh сообщает, сколько записей импортировано и сколько пропущено и почему.

Обход, gpg, разбор и отчёт: [import-export.md §1](docs/spec/import-export.md#1-import-from-pass-49).

### 4.10 Предупреждение об откате

Тот, у кого есть доступ на запись к копии (облачная папка, флешка), не может подделать хранилище, но может вернуть на место более старую действительную копию. passh предупреждает об этом. Предупреждение включено по умолчанию; `rollback.warn = false` отключает его.

- Для каждого `vault_id` passh записывает наибольшую `revision`, которую он открывал или сохранял на этой машине, в `~/.local/state/passh/revisions.json`. В файле только идентификаторы, номера ревизий и время.
- Если хранилище открывается с `revision` меньше записанной, passh предупреждает: «this copy is older than one seen before on this machine (r40 of 2026-11-10; seen r42 of 2026-11-15). If you didn't restore it on purpose, the file may have been replaced.»
  - Если есть терминал, passh спрашивает, продолжать ли. Да: меньшая ревизия становится новой записью, и предупреждение больше не повторяется. Нет: команда завершается без изменений. В TUI ответ «нет» при разблокировке завершает TUI, а ответ «нет» при перечитывании (`R`) отменяет перечитывание: остаются прежние данные, и сохранение остаётся заблокированным.
  - Без терминала предупреждение выводится в stderr, а команда продолжает работу; запись не меняется.
- Намеренное восстановление из резервной копии (§4.7) вызывает предупреждение один раз; ответьте «да».
- Запроса нет для файлов из папки автоматических резервных копий, для `verify --full` (он только сообщает результат сравнения) и для второго файла в `merge`.
- Проверка работает только на машине, которая видела более новую ревизию. Машина, впервые открывающая хранилище, откат обнаружить не может.

Формат журнала ревизий и когда он обновляется: [storage.md §7](docs/spec/storage.md#7-rollback-record-410). Должен ли его обновлять `verify --full` — открытый вопрос (§14).

### 4.11 Слияние (v1.1)

```
passh merge <file> [--dry-run]
```

Сливает другую копию того же хранилища с этим: после правок на двух машинах или с копией конфликта от инструмента синхронизации (например, `vault.sync-conflict-….passh`).

- У другого файла должен быть тот же `vault_id`; копии разных хранилищ отклоняются.
- Сначала passh пробует ключ этого хранилища на блоке данных другого файла, поэтому для копии с тем же ключом хранилища дополнительная парольная фраза не нужна. Если для другой копии выполнялся `rekey`, passh запрашивает её парольную фразу или бумажный ключ. В результате всегда остаётся блок ключа этого хранилища.
- Записи сопоставляются по `id`:

  | Случай | Результат |
  |---|---|
  | Только в одной копии, в другой нет надгробия | Сохраняется |
  | Одинакова в обеих | Сохраняется |
  | Различается в обеих | Побеждает более поздний `updated_at`; сообщается как конфликт |
  | В одной копии запись, в другой надгробие | Побеждает более позднее из `updated_at` и `deleted_at`: запись сохраняется или удаляется; сообщается |
  | Два разных `id` с одним `path` | Сохраняются обе; к имени записи из другого файла добавляется `~2` (или `~3`, …); сообщается |

- Надгробия из обеих копий сохраняются.
- Результат — одно сохранение (§4.6) с `revision` = большая из двух + 1. Другой файл не меняется; чтобы обновить его, скопируйте объединённое хранилище поверх него.
- `--dry-run` выводит отчёт без сохранения: добавленные, изменённые и удалённые записи, конфликты и переименования, по путям. Значения никогда не выводятся.
- Конфликты решаются по часам двух машин, поэтому неверные часы могут выбрать не ту сторону. Проигравшая версия остаётся в другом файле и в автоматических резервных копиях.

## 5. Сессия и безопасность

### 5.1 Разблокировка

- passh сам запрашивает парольную фразу в `/dev/tty` с отключённым эхо. Ни gpg, ни pinentry нет.
- Парольная фраза расшифровывает блок ключа, при этом один раз выполняется scrypt: около секунды на ноутбуке, несколько секунд и 256 МиБ памяти на Raspberry Pi. Всё дальнейшее использует ключ хранилища и работает быстро.
- После разблокировки весь блок данных расшифровывается и хранится в памяти.
- Команда получает ключ хранилища, по порядку:
  1. от агента, если он запущен для этого хранилища (§5.3);
  2. через запрос парольной фразы, если есть терминал (команда при этом не запускает агент);
  3. иначе завершается ошибкой «vault is locked: run `passh unlock` in a terminal (over SSH: `ssh -t host passh unlock`)».

Как обрабатывается каждый ответ агента: [agent-session.md §A2.8](docs/spec/agent-session.md#a28-where-the-key-comes-from-spec-51).

### 5.2 Блокировка

TUI блокируется, когда:

- пользователь нажимает `L` — кроме текстового поля (форма записи, запрос ввода или поиск во время набора), где `L` — обычная буква;
- TUI завершается;
- TUI бездействует в течение `session.idle_ttl`;
- passh получает SIGHUP, SIGTERM или SIGINT, например при обрыве SSH-соединения.

При блокировке passh стирает из своей памяти расшифрованные данные и ключ хранилища. Если включён `session.stop_agent`, он также останавливает агент. Блокировка клавишей `L`, по бездействию или по сигналу ещё и сразу очищает буфер обмена, если его очистка ожидается (§6.3). Выход из TUI, напротив, дожидается очистки буфера обмена, показывая обратный отсчёт; Ctrl-C очищает его сразу.

`passh lock` останавливает агент. Уже открытый TUI сохраняет собственное состояние, пока не заблокируется по правилам выше.

Что и в каком порядке делает блокировка и что сообщает экран блокировки: [tui.md §10](docs/spec/tui.md#10-locking-52).

### 5.3 Агент

Агент делает то, что gpg-agent делал для pass: держит хранилище разблокированным ограниченное время, чтобы последующие команды, в том числе без терминала, не спрашивали парольную фразу (ADR-8).

- **Запуск:** его запускает только `passh unlock [--ttl d]`. Команда запрашивает парольную фразу, запускает копию passh в фоне (как `ssh-agent`) и передаёт ей ключ хранилища через канал (pipe), но никогда — в аргументах или переменных окружения. Если агент уже запущен для того же блока ключа, `unlock` сообщает, сколько времени ему осталось, и перезапускает его таймер простоя; агент со старым блоком ключа (после `passwd` в другом месте) заменяется. Никакая другая команда, включая TUI, агент не запускает.
- **Один агент на хранилище**, на сокете `~/.local/state/passh/agent/agent-<hash of the vault's real path>.sock` (в `$XDG_STATE_HOME`). Папка агента имеет права 0700, сокет — 0600; passh проверяет, что это настоящая папка (не символическая ссылка) и что она принадлежит пользователю.
  - Сокет не лежит в `$XDG_RUNTIME_DIR`: система удаляет эту папку, когда заканчивается последняя сессия пользователя, а агент должен пережить SSH-сессию, которая его запустила.
  - Если путь слишком длинный для Unix-сокета (больше 103 байт: предел macOS, который действует и в Linux), passh использует `passh-<uid>/` в `$TMPDIR` или `/tmp` с теми же проверками.
  - Если файл сокета удалён или заменён, агент завершается.
- **Доступ:** агент отвечает только процессам того же пользователя; это проверяется по учётным данным собеседника (`SO_PEERCRED` в Linux, `getpeereid` в macOS). Он отдаёт ключ хранилища командам passh и никогда не пишет его на диск.
- **Время жизни:** агент завершается при первом из следующих событий:
  - `agent.idle_ttl` (по умолчанию 15 мин) без запросов ключа (запросы состояния не считаются);
  - `agent.max_ttl` (по умолчанию 2 ч; `unlock --ttl` переопределяет) с момента запуска;
  - `passh lock`;
  - блокировка TUI при включённом `session.stop_agent`;
  - `passwd`, `recover` или `rekey` этого хранилища (§5.4);
  - SIGTERM или SIGINT. SIGHUP агент игнорирует.

  Он переживает завершение SSH-сессии, в которой был запущен; в этом и состоит его назначение (§6.4).
- При завершении он стирает ключ хранилища из памяти и удаляет сокет.

Путь сокета, проверки папки, процедура запуска, протокол и истечение срока: [agent-session.md §A2](docs/spec/agent-session.md#a2-agent-spec-53).

### 5.4 Парольная фраза, смена ключа и ключ восстановления

- `passh init [--vault file]` дважды запрашивает новую парольную фразу, создаёт ключ хранилища и `vault_id`, записывает пустое хранилище и конфигурационный файл, если его нет. Затем предлагает распечатать ключ восстановления.
- **Стойкость парольной фразы:** `init`, `passwd`, `rekey` и `recover` оценивают стойкость парольной фразы (zxcvbn), предупреждают, если она слабая (оценка ниже 3 по шкале 0–4), и советуют 6 или больше случайных слов. Они не отказывают. Украденный файл хранилища можно атаковать офлайн, поэтому парольная фраза — его основная защита (§9).
- `passwd` и `rekey` всегда запрашивают текущую парольную фразу, даже если агент запущен, чтобы процесс, у которого есть доступ к агенту, не мог сменить парольную фразу или заменить ключ хранилища.
- `passh passwd` меняет парольную фразу: записывает новый блок ключа для того же ключа хранилища, поэтому ключ хранилища, а с ним и бумажный ключ восстановления, остаётся действительным. Как и любое изменение, это полное сохранение (§4.6): `revision` + 1, новый `saved_at`, блок данных зашифрован заново, сделана автоматическая резервная копия.
- `passh rekey` создаёт новый ключ хранилища, перешифровывает на него данные и запрашивает парольную фразу (ту же или новую). Старый бумажный ключ и старый блок ключа больше не открывают новые версии файла. Используйте эту команду, если парольная фраза или бумажный ключ могли утечь.
- `passwd`, `recover` и `rekey` останавливают агент этого хранилища, у которого остались старый блок ключа или старый ключ (§5.3); при необходимости снова выполните `passh unlock`.
- После `passwd` или `rekey` более старые копии и резервные копии по-прежнему открываются тем, что было действительно на момент их создания.
- **Бумажный ключ восстановления:** `passh recovery-key print [-o file]` для текстового листа или `--web` для страницы печати (§7.4). Лист содержит:
  - ключ хранилища (`AGE-SECRET-KEY-1…`) группами по четыре символа, а на странице печати ещё и в виде QR-кода;
  - `vault_id` и дату печати;
  - предупреждение, что владелец листа и копии хранилища может прочитать всё;
  - шаги ручного восстановления из §8 с командами байт в байт как там; на листах `ru` и `sr` переведён только комментарий `# asks for the passphrase`.

  Для печати, в том числе с `--web`, нужен терминал и ввод `PRINT RECOVERY KEY`. Для выходного файла действуют правила §7.2.
- `passh recover [--vault file]` запрашивает бумажный ключ, открывает им хранилище, запрашивает новую парольную фразу и записывает новый блок ключа (полное сохранение, как у `passwd`). Пробельные символы любого вида (пробелы, переводы строк), дефисы и регистр латинских букв во введённом ключе игнорируются, а встроенная контрольная сумма ключа (bech32) ловит опечатки.

Блоки ключа и данных, как их меняет каждая операция, раскладка и проверки ключа восстановления: [vault-format.md §3](docs/spec/vault-format.md#3-keys-and-encryption-41-54-adr-6).

### 5.5 Встроенные правила безопасности

Они не требуют настройки и не затрагивают систему:

| Правило | Подробности |
|---|---|
| S1 | passh никогда не записывает открытый текст на постоянный диск. Хранилище, его временный файл и резервные копии содержат только шифротекст. `edit --editor` использует временный файл на tmpfs (`$XDG_RUNTIME_DIR` или `/dev/shm`) с правами 0600 и затем удаляет его. tmpfs passh ищет только в Linux: в других системах (macOS), даже если tmpfs смонтирована, `edit --editor` вместо редактора открывает встроенную форму и выводит примечание |
| S2 | Секреты никогда не передаются как аргументы или переменные окружения. Парольная фраза читается из `/dev/tty`; ключ хранилища попадает к агенту через канал (pipe), а к клиентам — через сокет; при `import pass` gpg возвращает открытый текст в stdout |
| S3 | Для генерации паролей используется `crypto/rand` с выборкой с отклонением (rejection sampling, без смещения по модулю). Длина по умолчанию 24, из букв и цифр; `--symbols` добавляет 32 знака пунктуации ASCII. Другой алфавит настроить нельзя ([import-export.md §3](docs/spec/import-export.md#3-password-generator-s3)) |
| S4 | При выводе в терминал управляющие символы и escape-последовательности из содержимого записей экранируются, поэтому запись не может управлять вашим терминалом, например внедрив запись в буфер обмена через OSC 52. `show --raw` выводит байты как есть |
| S5 | В TUI пароли скрыты маской фиксированной длины; показанный пароль снова скрывается через 10 с |
| S6 | Буфер обмена очищается через `clipboard.clear_after`, если сессия ещё жива (по мере возможности) |
| S7 | Дампы памяти (core dumps) отключены (`setrlimit`) для passh и агента, и это затрагивает только эти процессы |
| S8 | Внешние программы (`$EDITOR`, команда буфера обмена и gpg только для `import pass`) запускаются без shell, со списками аргументов и, для программ, которые это принимают, с `--` перед путями. Результаты gpg читаются из `--status-fd`, а не из вывода, предназначенного для человека |
| S9 | Открытый получатель ключа хранилища (`age1…`) никогда не записывается в хранилище, резервные копии, экспорт, журналы и вывод (§4.1) |

Намеренно не предусмотрено (ADR-4):

- заблокированная или невыгружаемая память: `doctor` предупреждает, если swap включён;
- обнаружение отката на машине, которая ни разу не видела более новую ревизию хранилища (§4.10).

Как выполняется каждое правило: [agent-session.md §A9](docs/spec/agent-session.md#a9-safety-rules-how-they-are-met).

### 5.6 Редактирование

- `passh edit <path>` открывает встроенную форму: отдельные поля для пароля, имени пользователя, url и тегов и текстовую область для заметок. Однострочные поля не принимают переводы строк.
- `passh edit --editor <path>` открывает текстовую форму записи (§4.3) в `$EDITOR` (если он не задан — в `$VISUAL`, иначе в `vi`), разбитом на слова без shell, через временный файл по правилу S1. Для известных редакторов passh добавляет флаги, защищающие от утечек:
  - vim: `-n -u NONE -i NONE -c "set nobackup nowritebackup noundofile noswapfile"`;
  - neovim: `-n --clean -i NONE -c "set nobackup nowritebackup noundofile noswapfile"`;
  - nano: `--ignorercfiles --nohelp`.

  Для остальных редакторов выводится предупреждение, что passh не может контролировать их файлы резервных копий.

Клавиши и раскладка формы: [tui.md §11](docs/spec/tui.md#11-entry-form-56); внешний редактор по шагам: [agent-session.md §A6](docs/spec/agent-session.md#a6-external-editor-edit---editor-spec-56-s1).

## 6. Интерфейсы

### 6.1 CLI

Запуск `passh` без аргументов открывает TUI.

| Команда | Описание |
|---|---|
| `passh init [--vault file]` | Создать новое хранилище и конфигурационный файл, если его нет (§5.4) |
| `passh import pass [dir] [--overwrite] [--dry-run]` | Односторонний импорт из хранилища pass (§4.9) |
| `passh ls [folder] [--tag t]` | Вывести дерево, при необходимости с фильтром по тегу |
| `passh find <query>` | Нечёткий поиск по путям и тегам |
| `passh show <path> [--field f] [--raw]` | Вывести запись (текстовая форма, §4.3) или одно поле |
| `passh copy <path> [--field f]` | Скопировать в буфер обмена (§6.3) |
| `passh add <path> [-f\|--force]` | Интерактивное добавление: пароль (или генерация), имя пользователя, url, теги, заметки |
| `passh generate <path> [len] [--symbols] [-f\|--force]` | Сгенерировать и сохранить пароль |
| `passh edit <path> [--editor]` | Встроенная форма или `$EDITOR` (§5.6) |
| `passh mv <src> <dst>` / `passh rm <path> [-f\|--force]` | Переместить или удалить; `rm` сначала спрашивает подтверждение, если не указан `--force` (без терминала он обязателен) |
| `passh tag <path> --add a --remove b` / `passh tags` | Изменить теги / вывести список тегов с количеством записей |
| `passh unlock [--ttl d]` / `passh lock` | Запустить / остановить агент (§5.3) |
| `passh passwd` / `passh rekey` | Сменить парольную фразу / создать новый ключ хранилища (§5.4) |
| `passh recovery-key print [-o file] [--web]` / `passh recover` | Распечатать бумажный ключ восстановления / открыть им хранилище и задать новую парольную фразу (§5.4) |
| `passh verify [file] [--full]` | Проверить хранилище или копию (§4.8) |
| `passh backup <dest>` / `passh backups` | Сделать проверенную копию / вывести список автоматических резервных копий (§4.7, §4.8) |
| `passh merge <file> [--dry-run]` | Слить другую копию того же хранилища с этим (v1.1, §4.11) |
| `passh export …` / `passh print …` | §7 |
| `passh doctor` | Проверить конфигурацию, файл хранилища (структура, права 0600, доступность папки на запись, оставшиеся временные файлы), папки состояния и агента, агент, свободную память для разблокировки (scrypt нужно 256 МиБ; в macOS оценивается общий объём памяти), swap и поддержку буфера обмена в терминале. Только чтение: сообщает о проблемах, но никогда их не исправляет |
| `passh version` / `passh --version` / `passh -v` | Вывести `passh <version>` |
| `passh help [command…]` | То же, что `passh <command…> --help` |

Глобальные флаги: `--config <file>`, `--vault <file>`. У каждой команды есть `-h`/`--help`. Если у команды есть `--output` (`export`, `print`, `recovery-key print`) или `--force` (`add`, `generate`, `rm`), их короткие формы — `-o` и `-f`.

Командам, которые читают или меняют записи, нужен ключ хранилища (§5.1). `init`, `verify` без `--full`, `backup`, `backups`, `lock`, `doctor`, `version` и `help` обходятся без него.

Синтаксис, флаги, запросы ввода, вывод, сообщения и коды завершения каждой команды: [cli.md](docs/spec/cli.md).

### 6.2 TUI

Построен на Bubble Tea + Bubbles + Lip Gloss (charmbracelet). Макет ниже справочный (tui.md §5.1):

```
┌ passh ── unlocked · locks in 4:12 ───────────────────────────────────────────┐
│ VIEW: [Folders]  Tags                                               / search │
├───────────────────────────┬──────────────────────────────────────────────────┤
│ ▸ bank                (3) │ work/github                                      │
│ ▸ homelab             (7) │ username  arsenii                                │
│ ▾ work               (12) │ password  ••••••••               [c]opy [r]eveal │
│     confluence            │ url       https://github.com                     │
│     github                │ tags      work · dev · 2fa                       │
│     jira                  │ notes     Recovery codes in notes…               │
├───────────────────────────┴──────────────────────────────────────────────────┤
│ c copy pw · u copy user · r reveal · e edit · a add · t tags · d delete      │
│ Tab folders/tags · / search · P print · R reload · L lock · ? help · q quit  │
└──────────────────────────────────────────────────────────────────────────────┘
```

- **Два представления**, переключаются клавишей `Tab`:
  - *Folders* (папки): сворачиваемое дерево путей записей;
  - *Tags* (теги): список тегов с количеством записей; при выборе тегов показываются их записи (логическое И).
- `/` открывает нечёткий поиск по путям и тегам.
- `d` удаляет запись, `m` перемещает или переименовывает её, `R` перечитывает хранилище, а `P` открывает выбор того, что печатать, и затем страницу печати (§7.4). Разрушительные действия требуют подтверждения.
- Экран блокировки запрашивает парольную фразу или берёт ключ у агента, если тот запущен.
- Если файл хранилища изменился на диске, пока открыт TUI, TUI показывает «vault changed on disk — R to reload», и сохранение заблокировано до перезагрузки (§4.6).
- В узких терминалах (уже 80 столбцов, например на телефонах) используется одна панель: список → Enter → подробности → Esc.
- Все значения выводятся с учётом S4.

Экраны, все клавиши, правила раскладки и сообщения: [tui.md](docs/spec/tui.md).

### 6.3 Буфер обмена

- **OSC 52** (`clipboard.osc52`): passh записывает значение через терминал (`ESC ] 52 ; c ; <base64> BEL`). Это работает локально и по SSH в терминалах с такой поддержкой: iTerm2, kitty, WezTerm, Windows Terminal, Alacritty, tmux с `set-clipboard on` и Termux с включённой настройкой OSC 52.
- **Локальная утилита** (`clipboard.command`): например, `["pbcopy"]`, `["wl-copy"]` или `["xclip", "-selection", "clipboard"]`. passh передаёт значение через stdin. Это полезно там, где терминал не поддерживает OSC 52, например в macOS Terminal.app.
- **Очистка:** через `clipboard.clear_after` passh тем же способом отправляет пустое значение. `passh copy` перед завершением дожидается очистки; так же поступает и TUI при выходе (с обратным отсчётом; Ctrl-C очищает сразу). Блокировка TUI очищает буфер сразу (§5.2).
- **Нет ни того, ни другого:** `copy` завершается ошибкой с подсказкой (`passh show <path> --field password | pbcopy`). Секрет при этом не выводится.
- `passh doctor` отправляет тестовую строку и затем очищает её, чтобы вы могли проверить свой терминал.
- История буфера обмена на клиенте (Universal Clipboard в macOS, Android, менеджеры буфера обмена) может сохранять копии. В README сказано, что терминал нужно исключить из этих инструментов.

Выбор способа, отправляемые байты, расписание очистки и сообщения: [agent-session.md §A5](docs/spec/agent-session.md#a5-clipboard-spec-63-s6).

### 6.4 По SSH

Специального серверного режима нет; passh — это просто команда на удалённой машине:

```bash
ssh -t pi passh                                       # TUI
ssh pi passh show work/github --field password | pbcopy
```

- TUI и запросам ввода нужен терминал, поэтому используйте `ssh -t`.
- Чтобы передать секрет с сервера через конвейер, сначала запустите агент командой `ssh -t pi passh unlock`. После этого команды без `-t` работают, пока агент не завершится (§5.3); `ssh pi passh lock` останавливает его.
- Для экспорта данных нельзя использовать `-t`: PTY превращает LF в CRLF и подмешивает stderr в поток (§7.1).

## 7. Экспорт и печать

### 7.1 Экспорт

```
passh export --format <csv|json|bitwarden-json> [--tag t] [--folder f] [-o file]
             [--age <recipient> | --confirm-plaintext] [--spreadsheet-safe]
```

Экспорт нужен, чтобы перенести данные в другие инструменты. Для резервной копии хранилища скопируйте файл (§4.8).

| Формат | Содержимое | Назначение |
|---|---|---|
| `json` | Формат данных из §4.2 (§7.3) | Скрипты, миграция |
| `csv` | `folder,name,username,password,url,tags,notes`, кавычки по RFC 4180 | KeePassXC и другие |
| `bitwarden-json` | Схема незашифрованного экспорта Bitwarden | Vaultwarden/Bitwarden |

Любой формат — открытый текст, если только `--age <recipient>` не шифрует его на открытый ключ age: получателя X25519 (`age1…`) или гибридного постквантового получателя (`age1pq1…`). Зашифрованный вывод всегда записывается в ASCII-броне.

Соответствие полей:

- `csv`: теги объединяются через `, `; для дополнительных полей столбца нет, они не попадают в файл, passh об этом предупреждает.
- `bitwarden-json`: папки становятся папками Bitwarden с именем по пути (`work/sub`), причём перечисляются и все родительские папки; `login.totp` — первое поле с именем `otp` (в любом регистре), а если такого нет — первое значение, начинающееся с `otpauth://`; остальные поля становятся пользовательскими полями, скрытыми, если ключ — `password` или `otp` (в любом регистре) или значение начинается с `otpauth://`; теги — одним пользовательским полем `tags` через `, `.

Правила:

- **Экспортируемые данные никогда не выводятся в терминал.** Используйте `-o file` или перенаправьте stdout.
- **Открытый текст** (без `--age`) требует подтверждения:
  - если у passh есть терминал, пользователь вводит `EXPORT PLAINTEXT` в `/dev/tty`;
  - иначе требуется `--confirm-plaintext`.
- **`-o file`** создаёт файл с правами 0600. Если файл находится не на tmpfs, passh предупреждает, что открытый текст попадёт на постоянный диск.
- **Значения в CSV по умолчанию выводятся без изменений**, потому что файл предназначен для менеджера паролей. `--spreadsheet-safe` добавляет `'` в начало ячеек, которые начинаются с `= + - @`, табуляции или CR, чтобы предотвратить внедрение формул в электронных таблицах. Это меняет значения, включая пароли, поэтому не импортируйте такой файл в менеджер паролей.

Порядок проверок и все форматы байт в байт: [import-export.md §2](docs/spec/import-export.md#2-export-71-73).

### 7.2 Печать

```
passh print [--tag t] [--folder f] [--fields password,username,url] [-o file] [--confirm-plaintext]
passh print --web [--tag t] [--folder f] [--fields …]
```

- Действуют те же правила подтверждения, что и для экспорта открытого текста (§7.1).
- Без `--web`: текстовый лист — моноширинная вёрстка с разбивкой на страницы и группировкой по папкам, неоднозначные символы помечены (`0/O`, `1/l/I`), на каждой странице дата печати и CONFIDENTIAL (на языке из §3.3).
- `--web`: страница печати (§7.4) — способ печати из браузера; браузер может и сохранить её как PDF.
- Вывода в PDF нет (убран в v0.6, чтобы не раздувать бинарник: его заменяет страница печати).
- Распечатайте файл, затем удалите его; в README отмечено, что листы, оставленные на диске, например PDF, сохранённый браузером в «Загрузки», — это утечка.
- У бумажного ключа восстановления свой лист (§5.4).

Оба листа построчно и их разбивка на страницы: [print.md](docs/spec/print.md).

### 7.3 Экспорт в JSON

Формат `json` — это формат данных из §4.2 с добавленным `exported_at` и без `deleted`, поэтому `vault_id`, `id` записей и метки времени сохраняются.

### 7.4 Страница печати (веб)

Одноразовая HTTPS-страница с листом паролей. Вы открываете её в браузере на другом устройстве в LAN или VPN, печатаете, и при этом ничего нигде не сохраняется.

**Запуск**

- Требуется `print_web.enabled = true`.
- Запускается из TUI клавишей `P`, которая сначала спрашивает, что печатать (все записи, папку или выбранные теги; какие поля), или командой `passh print --web …`. Нужен терминал, и для подтверждения пользователь вводит `PRINT`.
- passh показывает:
  - URL для каждого адреса привязки и его QR-код для телефонов; TUI показывает один URL с его QR-кодом за раз, а Tab переключает на следующий;
  - отпечаток сертификата и обратный отсчёт.

  `c` копирует показанный URL в буфер обмена.
- Сервер работает внутри процесса passh; демона нет.

**Сеть**

- Слушает только на адресах интерфейсов из `print_web.interfaces` и только на **частных** адресах: RFC 1918, `100.64.0.0/10` (Tailscale) и IPv6 ULA `fc00::/7`.
  - Публичный адрес отклоняется.
  - Привязка к `0.0.0.0` или `::` никогда не выполняется.
- Соединения от клиентов вне разрешённых диапазонов закрываются до TLS. По умолчанию это подсети адресов привязки; для адреса без подсети (/32 или /128, как выдаёт Tailscale) — частный диапазон, в который он входит (например, `100.64.0.0/10`). Непустой `allow_from` заменяет диапазоны по умолчанию (открытый вопрос в §14).
- Заголовок `Host` должен содержать адрес привязки или одно из имён `hostnames`, что защищает от DNS rebinding.
- passh не открывает порты в брандмауэре. Если брандмауэр блокирует порт, открыть его — ваша задача.

**Сертификат**

- **Никакого CA, ничего не устанавливается ни на одно устройство.** При первом использовании passh создаёт самоподписанный сертификат (ECDSA P-256, действителен 1 год) для адресов привязки и `hostnames`.
- Он хранит сертификат в `~/.local/state/passh/print-web/` (ключ с правами 0600) и использует его повторно, поэтому отпечаток не меняется.
- Если адреса изменились или срок действия сертификата истёк, passh создаёт новый и сообщает об этом.
- **Первый заход с устройства:** браузер предупреждает о сертификате. Сравните отпечаток SHA-256, который показывает браузер, с тем, который показывает passh, и только затем примите сертификат. Firefox может запомнить исключение навсегда; после этого любой другой сертификат на этом адресе снова вызовет предупреждение. Если принять сертификат без сравнения, вы останетесь уязвимы для активного атакующего в LAN (§9).
- Только TLS 1.3. Обычный HTTP никогда не предлагается.

**Токен и время жизни**

- URL имеет вид `https://<address>:<port>/p/<token>`, где токен — 128-битное случайное значение (`crypto/rand`, base64url).
- **Страница отдаётся один раз.** Первый `GET` с правильным токеном расходует его, и сервер останавливается после того, как ответ записан.
- Сервер также останавливается при первом из следующих событий:
  - истечение `print_web.ttl`, по умолчанию 5 мин, максимум 15;
  - блокировка (§5.2);
  - завершение passh;
  - `Esc` в диалоге печати;
  - 5 запросов к `/p/` с неверным токеном. Другие пути, например `/favicon.ico`, получают 404 и не учитываются.
- Предпросмотр ссылок и предварительная загрузка в браузере могут израсходовать токен раньше пользователя. Сервер тогда уже остановлен, и браузер пользователя не может подключиться; passh показывает, какой адрес получил страницу («served to 192.168.1.23»), поэтому пользователь это замечает и запускает страницу заново. Запрос, пришедший, пока страница ещё передаётся, получает «already used».

**Страница**

- То же содержимое, что у текстового листа (§7.2), свёрстанное для печати.
- Без JavaScript, внешних шрифтов и изображений. Пользователь печатает через Ctrl/Cmd+P.
- Страница формируется из памяти в момент поступления запроса и передаётся потоком. Каждое значение экранируется через `html/template` и дополнительно по S4.
- Заголовки ответа:
  ```
  Cache-Control: no-store
  Content-Security-Policy: default-src 'none'; style-src 'sha256-…'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
  Referrer-Policy: no-referrer
  X-Content-Type-Options: nosniff
  ```
  CSP блокирует скрипты и все исходящие запросы, поэтому даже при сбое экранирования страница не смогла бы никуда отправить пароли.
- После печати закройте вкладку. Браузеры могут сохранить страницу для восстановления сессии, а «Сохранить как PDF» или очереди печати могут оставлять файлы.

Адреса, сертификат, обработка запросов, результаты, HTML и CSS страницы и диалог в терминале: [print.md §6](docs/spec/print.md#6-print-page-server).

## 8. Резервное копирование и восстановление

| Что | Как |
|---|---|
| Файл хранилища | Копируйте его куда угодно и сколько угодно раз: он зашифрован. `passh backup <dest>` делает проверенную копию, а `passh verify` проверяет любую копию (§4.8). Кроме того, passh хранит 10 последних версий на этой машине (§4.7) |
| Парольная фраза | Помните её. Используйте 6 или больше случайных слов |
| Бумажный ключ восстановления | `passh recovery-key print` один раз и снова после `rekey` (§5.4). Открывает любую копию, сделанную с этим ключом хранилища, если парольная фраза забыта. Храните его офлайн, как наличные |
| Конфигурационный файл | Не обязателен; в нём только путь к хранилищу и настройки |

**Переезд на новую машину:**

1. скопируйте бинарный файл `passh`;
2. скопируйте файл хранилища и выполните `passh verify --full <file>`;
3. напишите конфигурационный файл (`vault = "…"`) или используйте `--vault`.

**Забыта парольная фраза:** `passh recover` с бумажным ключом (§5.4).

**Без passh**, на любой машине с [age](https://age-encryption.org) версии 1.0 или новее:

```bash
tr -d '\r' < vault.passh | awk '/BEGIN AGE ENCRYPTED FILE/{n++} n==1{print} n==1 && /END AGE ENCRYPTED FILE/{exit}' > key.age
tr -d '\r' < vault.passh | awk '/BEGIN AGE ENCRYPTED FILE/{n++} n==2{print} n==2 && /END AGE ENCRYPTED FILE/{exit}' > data.age
age -d -o /dev/shm/key.txt key.age                            # asks for the passphrase
age -d -i /dev/shm/key.txt -o /dev/shm/vault.json data.age
rm /dev/shm/key.txt
```

- С бумажным ключом вместо парольной фразы пропустите первую и третью команды: запишите ключ в `/dev/shm/key.txt` одной строкой без пробелов, затем выполните вторую, четвёртую и пятую.
- `vault.json` — открытый текст (§4.2). Держите его на tmpfs (`/dev/shm` в Linux) и удалите после использования.
- Если почтовый клиент или редактор перенёс строки, `age` может отклонить блоки. passh такой файл всё равно открывает (§4.5), а `passh backup` записывает его обратно в канонической форме.

Файлы с окончаниями строк только CR и точный вид `key.txt`: [vault-format.md §8](docs/spec/vault-format.md#8-notes-on-recovery-without-passh-8).

## 11. Архитектурные решения

**ADR-1: Собственный файл хранилища, зашифрованный age; без GnuPG и git.** Решение владельца в v0.6: совместимость с pass не нужна; важен один файл, который переживает копирование. age — небольшой, хорошо специфицированный формат с несколькими независимыми реализациями (Go, Rust, TypeScript), а его библиотека для Go написана на чистом Go, поэтому passh остаётся одним статическим бинарным файлом без зависимостей во время выполнения. Если passh когда-нибудь станет недоступен, хранилище откроет стандартная утилита `age` (§8). Цена: общего хранилища с `pass` больше нет; `import pass` работает в одну сторону. Это заменяет решение v0.5 «использовать системный gpg».

**ADR-2: Папки остаются основным способом организации; теги дополняют их.** Теги хранятся в самих записях. Поскольку после разблокировки всё хранилище находится в памяти, индекс не нужен.

**ADR-3: Обычная CLI-утилита, которая не меняет систему.** Решение владельца в v0.5: один бинарный файл, один конфигурационный файл, запуск как обычной команды. Это заменяет модель ограниченного SSH-сервера из v0.2–v0.4. Начиная с v0.6 есть один фоновый процесс — агент, который запускается только командой `passh unlock` и завершается сам (ADR-8). Компромисс: прав для отдельных устройств нет, и любой, кто может войти в систему под вашей учётной записью, получает полный доступ к passh.

**ADR-4: Минимальная защита.** Решение владельца в v0.5 остаётся в силе: без подписанной истории, без заблокированной памяти, только дешёвые правила из §5.5, не требующие настройки. В v0.6 формат файла бесплатно добавляет немного защиты: имена и теги зашифрованы, а изменённый файл не открывается (S9). Откат к более старой действительной копии вызывает только предупреждение, и только на машине, которая видела более новую ревизию (§4.10).

**ADR-5: Страница печати в LAN/VPN по HTTPS с самоподписанным сертификатом.** passh не должен менять хранилища доверенных сертификатов на устройствах, поэтому вместо локального CA он использует постоянный самоподписанный сертификат и проверку отпечатка (§7.4).

**ADR-6: Два слоя в одном файле: блок ключа и блок данных.** Решение владельца в v0.6. Парольная фраза защищает случайный ключ хранилища, а ключ хранилища шифрует данные. В результате:

- scrypt выполняется один раз при разблокировке, а не при каждом сохранении или команде;
- агент хранит ключ, а не парольную фразу;
- `passwd` защищает тот же ключ хранилища новой парольной фразой, поэтому данные остаются зашифрованы тем же ключом;
- ключ хранилища одновременно служит бумажным ключом восстановления;
- ручное восстановление занимает две команды `age`.

Отвергнуто: один файл `age -p` (scrypt при каждом сохранении и каждой команде — на Pi это секунды на каждую — и парольная фраза в памяти) и собственный формат на Argon2id (его не смогла бы открыть ни одна стандартная утилита). Получатель остаётся секретным, потому что age не подтверждает отправителя (S9).

**ADR-7: Одно хранилище, одно основное место.** Решение владельца в v0.6: хранилище живёт в одном месте (на ноутбуке или на Pi, к которому обращаются по SSH), а остальные копии — резервные. Вместо слияния passh отказывается перезаписывать файл, который изменился после открытия (§4.6). У записей есть id, метки времени и надгробия, поэтому `passh merge` появится в v1.1 без изменения формата (§4.11).

**ADR-8: Агент passh вместо gpg-agent.** Решение владельца в v0.6. Он сохраняет сценарий `ssh -t pi passh unlock`, затем `ssh pi passh show … | pbcopy`. Агент запускается только командой `passh unlock`, обслуживает только того же пользователя и завершается сам по истечении времени бездействия и максимального времени (§5.3). Его роль и его риск те же, что у gpg-agent в v0.5.

## 13. Критерии приёмки (v1)

### 13.1 Функциональные

1. Установка сводится к копированию бинарного файла и запуску `passh init`; `passh doctor` не сообщает об ошибках.
2. `passh import pass` импортирует существующее хранилище pass с его папками, тегами и дополнительными полями. После этого passh работает и без установленного gpg.
3. TUI запрашивает парольную фразу один раз за сессию. После бездействия в течение `session.idle_ttl` запрашивает её снова.
4. После `ssh -t pi passh unlock` команда `ssh pi passh show … | pbcopy` работает без терминала. После `agent.idle_ttl` или `passh lock` процесса агента больше нет, и команда завершается ошибкой с подсказкой.
5. Копирование работает через OSC 52, локально и по SSH, а также через `clipboard.command`; буфер обмена очищается через 30 с.
6. Экспорт Bitwarden JSON импортируется в Vaultwarden. Экспорт CSV импортируется в KeePassXC, и пароли, начинающиеся с `= + - @`, остаются без изменений.
7. Страница печати, запущенная на Pi, открывается в браузере ноутбука через LAN и через VPN. После принятия сертификата (отпечаток совпадает) страница печатается, а сервер останавливается после загрузки.
8. Хранилище, скопированное через `scp`, через флешки с FAT32 и с exFAT, через облачную папку, как вложение в письмо и как вставленный текст (CRLF, перенесённые строки), открывается на другой машине — между Linux и macOS и между amd64 и arm. `passh verify` признаёт каждую копию исправной, а у побайтно точных копий SHA-256 совпадает с оригиналом.
9. Без passh шаги из §8 со стандартной утилитой `age` дают JSON хранилища — и с парольной фразой, и с бумажным ключом.
10. Если парольная фраза забыта, `passh recover` с бумажным ключом открывает хранилище и задаёт новую парольную фразу.

### 13.2 Тесты безопасности

1. Отклоняются пути с сегментами `.` или `..`, с пустыми сегментами, с ведущим `-` в любом сегменте или с управляющими символами. `import pass` не следует по символическим ссылкам, ведущим за пределы хранилища pass.
2. После любой команды, кроме явных `export -o` или `print -o`, на постоянном диске нет файлов с открытым текстом (тест по разнице состояний файловой системы). Хранилище, его временные файлы и резервные копии не содержат ни одного значения из записей.
3. Escape-последовательности (включая OSC 52) в содержимом записей отображаются обезвреженными в TUI и в `show`.
4. Сгенерированные пароли проходят тест равномерности хи-квадрат на 10⁶ выборках.
5. Экспорт открытого текста без подтверждения завершается ошибкой. Экспорт с подтверждением не содержит текста запроса. Запись экспортируемых данных в терминал отклоняется.
6. Агент:
   - папка агента имеет права 0700, сокет — 0600;
   - соединение от другого пользователя отклоняется;
   - агент завершается по `agent.idle_ttl`, по `agent.max_ttl`, по `passh lock` и при блокировке TUI с `session.stop_agent`;
   - ключ хранилища никогда не появляется в аргументах или окружении какого-либо процесса (`/proc/<pid>/cmdline`, `/proc/<pid>/environ`);
   - никакая команда, кроме `unlock`, не запускает агент.
7. Страница печати:
   - привязывается только к частным адресам;
   - отдаётся один раз;
   - неверный заголовок `Host` или клиент вне `allow_from` отклоняются;
   - останавливается по TTL и при блокировке;
   - заголовки ответа соответствуют §7.4, а headless-браузер, загрузивший страницу, не делает запросов по её инициативе (собственный фоновый трафик браузера не в счёт);
   - `<script>` или `<img>` в содержимом записи отображаются как текст.
8. Полная сессия (init, add, edit, unlock, export, страница печати, lock) ничего не пишет за пределами файла хранилища и его временного файла, конфигурационного файла, `~/.local/state/passh/`, папки агента в `/tmp`, если она используется, и временной папки на tmpfs (разница состояний файловой системы для `$HOME` и `/etc`, а также трассировка системных вызовов).
9. Сохранение:
   - сохранение, прерванное на любом шаге §4.6 (внедрение сбоя до и после каждого `fsync` и `rename`), оставляет хранилище, которое открывается, — со старой или с новой ревизией;
   - оставшиеся временные файлы удаляются при следующем сохранении;
   - хранилище, изменённое на диске после открытия, не перезаписывается;
   - из двух процессов passh, сохраняющих изменения в одно хранилище, второму отказывается, и ни одно изменение не теряется молча.
10. Повреждение и подмена:
    - изменение любого одного байта хранилища или его обрезка в любом месте даёт ошибку с названием проблемы и никогда не показывает данные частично (изменение, которое поглощают мягкие правила §4.5, например последний перевод строки, может вместо этого открыться с теми же данными);
    - блок данных, зашифрованный на другой ключ, отклоняется;
    - получатель (`age1…`) никогда не появляется в хранилище, резервных копиях, экспорте и выводе.
11. Предупреждение об откате:
    - при включённом `rollback.warn` открытие более старой копии хранилища, которое эта машина уже видела, вызывает предупреждение; если есть терминал, отказ завершает команду без изменений, а согласие прекращает повторы предупреждения;
    - без терминала предупреждение выводится в stderr, и запись не меняется;
    - файлы из папки автоматических резервных копий, `verify --full` и второй файл в `merge` никогда не вызывают запроса;
    - при выключенном `rollback.warn` предупреждений нет.

## 14. Открытые вопросы

Решения, которые должен принять владелец; их поднял аудит 2026-11-16. Приложения описывают текущее поведение; ошибки в коде, не требующие решения, перечислены в [docs/reviews/2026-11-16-spec-audit.md](docs/reviews/2026-11-16-spec-audit.md).

1. **`verify --full` и журнал ревизий.** По §4.10 `verify --full` только сообщает результат сравнения. Он никогда не задаёт вопроса, но, как и любое открытие, повышает запись в журнале, если видит более высокую ревизию; то же делает открытие файла из папки автоматических резервных копий через `--vault`. После проверки более новой копии (например, с другой машины) собственное хранилище этой машины при следующем открытии получит предупреждение об откате. Варианты: (a) оставить так и сказать об этом в §4.10; (b) открытия «только для отчёта» и файлы резервных копий никогда не меняют журнал.
2. **Файловые системы без `flock`.** Каждый временный файл (сохранение, автоматическая резервная копия, `passh backup`) на время записи блокируется через `flock`, чтобы очистка никогда не удалила незавершённую запись другого процесса; если `flock` не работает, сохранение или копирование завершается ошибкой (`locking the temporary file: …`). Это может касаться томов exFAT и FAT (msdos) в macOS, общих папок SMB и некоторых файловых систем FUSE, тогда как §4.8 обещает, что флешки с FAT32 и exFAT подходят. Нужна проверка на macOS. Варианты: (a) оставить `flock` и сузить §4.8 до проверенных файловых систем; (b) писать без блокировки там, где `flock` не поддерживается, отказавшись от этой гарантии; (c) так же, но только для целевых файлов `passh backup`.
3. **`import pass` и символические ссылки внутри хранилища.** По символическим ссылкам на папки внутри хранилища passh не переходит, а об абсолютной ссылке сообщает, что она ведёт наружу, даже если она указывает внутрь хранилища; сам `pass` следует по обеим. Варианты: (a) оставить как безопасный и простой вариант и описать это; (b) следовать по ссылкам на папки, не выходящим за пределы хранилища (с обнаружением циклов), а абсолютные цели разрешать относительно реального пути хранилища.
4. **`print_web.allow_from`.** Непустой `allow_from` заменяет диапазоны по умолчанию (подсети адресов привязки); комментарий в §3.3 называет его «extra CIDR limit» (дополнительное ограничение), а конфигурация принимает любой CIDR, включая публичные диапазоны и `0.0.0.0/0`. Варианты: (a) замена, как сейчас, и исправленный комментарий (и в шаблоне `passh init`); (b) пересечение с диапазонами по умолчанию, чтобы `allow_from` мог их только сужать. Отдельно: нужно ли отклонять `0.0.0.0/0`, `::/0` и публичные диапазоны.
5. **Коды завершения.** Сигнал завершает команду с кодом 128 + n во время запроса ввода и в TUI, с кодом 0 у `copy` (после очистки буфера обмена), с кодом 1 у диалога страницы печати и внешнего редактора, а в остальных случаях — действием сигнала по умолчанию. Предложение: везде 128 + n после уборки. Недопустимые пути, папки и теги в аргументах и неизвестные имена `--field` дают код 1, хотя passh описывает значение, которое не удаётся разобрать, как ошибку использования (2) — и так поступает с длиной у `generate` и с `print --fields`. Варианты: (a) оставить 1 для значений, которые проверяют валидаторы хранилища, и описать это; (b) сделать их ошибками использования (2).

Решено в v0.6: предупреждение об откате — настройка в конфигурации (§4.10); `merge` появится в v1.1 (§4.11); коэффициент сложности scrypt остаётся значением age по умолчанию, облегчённой настройки нет.
