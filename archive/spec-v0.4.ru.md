## 1. Краткое описание

passh — это один бинарный файл на Go для управления паролями на собственной машине (Raspberry Pi или VPS). Пользователи обращаются к нему по SSH с любого устройства в LAN или VPN. Он читает и пишет **совместимое с pass** хранилище: файлы, зашифрованные GPG, в git-репозитории. Поверх этого он добавляет:

- модель сессий: разблокировать один раз и пользоваться N минут; блокировка происходит автоматически по тайм-ауту или при выходе;
- права для каждого SSH-ключа: например, ноутбук может записывать и запускать скрипты, а телефон — только читать в интерактивном режиме;
- TUI для просмотра по папкам (категориям) и тегам;
- копирование в буфер обмена *клиента* по SSH (OSC 52) с очисткой по мере возможности;
- экспорт (CSV / JSON / зашифрованный архив), лист для печати (PDF / текст) и одноразовую страницу печати, которая открывается в браузере в LAN или VPN;
- защиту целостности: подписанный список получателей и подписанную историю;
- самодостаточную резервную копию: хранилище содержит собственный ключ, защищённый парольной фразой, поэтому для восстановления где угодно достаточно **резервной копии и парольной фразы**.

Все данные находятся на одном хосте, поэтому резервировать нужно только одно место.

## 2. Цели и что не входит в цели

### Цели

| # | Цель |
|---|------|
| G1 | Один статический бинарный файл на Go (`linux/arm64`, `linux/amd64`, `linux/arm/v7`), без зависимостей во время выполнения, кроме `gpg`, `git` и `ssh` |
| G2 | Совместимость со структурой хранилища `pass`. Существующие хранилища открываются без изменений (подпись добавляется при принятии, §4.4), а `pass` продолжает работать с хранилищем passh |
| G3 | Полноценная работа по SSH из SSH-клиентов для macOS, Linux, Windows, Android (Termux) и iOS |
| G4 | Одна разблокировка на сессию. Секреты забываются по истечении TTL или при завершении сессии |
| G5 | Просмотр и поиск по папкам и тегам в TUI |
| G6 | Экспорт и печать для миграции и автономной аварийной резервной копии, включая печать прямо из браузера без сохранения файла |
| G7 | Каждое изменение фиксируется подписанным коммитом в git. Резервное копирование = push одного репозитория. Резервной копии и парольной фразы достаточно, чтобы восстановить всё |
| G8 | Пользователь, которому по SSH доступен только passh, не может получить shell или выполнить произвольные команды через passh, а каждый SSH-ключ получает только перечисленные для него права |

### Что не входит в цели (v1)

- Расширения для браузеров, автозаполнение на мобильных устройствах, нативные мобильные приложения
- Совместный доступ нескольких пользователей, роли, разрешения (права для каждого ключа нужны для устройств одного владельца)
- Веб-интерфейс или HTTP API. Единственное исключение — одноразовая страница печати только для чтения (§7.4)
- Синхронизация между несколькими серверами. Удалённые репозитории git служат резервными копиями **только для push**
- Поддержка Windows/macOS в роли *сервера* (клиентам нужен только SSH)
- Защита от атакующего, который уже контролирует пользователя `vault` или root (§9)

## 3. Модель развёртывания

```
 ┌──────────────┐   WireGuard / Tailscale   ┌───────────────────────────────┐
 │ Laptop/Phone │ ─────────── SSH ────────▶ │ Raspberry Pi / VPS             │
 │ (any SSH     │                           │  user: vault                   │
 │  client)     │ ◀── OSC 52 clipboard ──── │  ~/.password-store  (git)      │
 └──────────────┘ ◀── HTTPS print page ──── │  ~/.gnupg           (key)      │
       (browser, on demand, LAN or VPN)     │                                │
                                            │  /usr/local/bin/passh (root:root 0755)
                                            │  /etc/passh/policy.toml (root:root 0644)
                                            └──────────┬────────────────────┘
                                                       │ git push only (append-only remote)
                                                       ▼
                                                 Backup target(s)
```

Расшифровка происходит **на сервере** (модель «A»). Это осознанный компромисс: никакой настройки на клиентах, но сервер становится ценной целью для атаки. См. §9.

passh запускается либо прямо на хосте (§3.1–3.4), либо в контейнере Docker (§3.5).

### 3.1 Требования к хосту

- **ОС:** Debian 12 / Raspberry Pi OS bookworm или новее. Минимальные версии, которые проверяются `doctor` и при запуске: git ≥ 2.32 (`GIT_CONFIG_GLOBAL`; версия 2.30 из bullseye молча игнорирует эту переменную), GnuPG ≥ 2.2.8 (отсутствие MDC — фатальная ошибка), OpenSSH ≥ 7.6 (`ExposeAuthInfo`).
- **Пользователь `vault`:** используется только для passh, без других сервисов. Пароль заблокирован (`passwd -l`). Оболочка входа — `/bin/sh`. Dot-файлы в `~vault` (`.profile`, `.bashrc`, …) принадлежат root, потому что sshd запускает `ForceCommand` через оболочку входа.
- **Бинарный файл:** `passh` принадлежит root, и `vault` не может в него писать.
- **Swap отключён или используется zram без writeback.** Raspberry Pi OS по умолчанию включает файл подкачки на SD-карте (`dphys-swapfile`), который может сохранить расшифрованные данные. passh читает `/proc/swaps` **при каждом запуске** и отказывается расшифровывать, если активен swap на диске. Гибернация не используется. В контейнере это правило также выполняется, если лимит swap в cgroup равен 0 (§3.5).
- **Синхронизация времени** (`systemd-timesyncd`). У Pi нет RTC; при неверных часах gpg сообщает о подписях «из будущего», и это выглядит как ложное нарушение целостности.
- Установлен **`systemd-container`** — для административного пути (`machinectl`, §3.4).
- **Межсетевой экран:** если страница печати включена (§7.4), её порт принимает соединения только из подсетей LAN и VPN.
- Шифрование всего диска или домашнего каталога рекомендуется, но не обязательно (записи и так зашифрованы; оно защищает метаданные).

### 3.2 Настройка SSH

`sshd_config`. Установщик записывает его и запускает `sshd -t` перед перечитыванием конфигурации, поэтому неверный шаблон не отрежет владельцу доступ к хосту без монитора и клавиатуры:

```
# global scope (not allowed inside Match)
PermitUserEnvironment no

Match User vault
    AuthenticationMethods publickey
    AuthorizedKeysFile /etc/ssh/authorized_keys/%u
    PasswordAuthentication no
    KbdInteractiveAuthentication no
    DisableForwarding yes
    PermitTunnel no
    PermitUserRC no
    PermitTTY yes
    ExposeAuthInfo yes
    ForceCommand /usr/local/bin/passh
```

`/etc/ssh/authorized_keys/vault` (root:root 0644, поэтому ни `vault`, ни ошибка в passh не могут добавить ключи):

```
restrict,pty ssh-ed25519 AAAA… laptop
restrict,pty ssh-ed25519 AAAA… phone
```

- `restrict` отключает всю переадресацию и пользовательские rc-файлы; `pty` снова разрешает только терминал.
- **Никаких `command=` для отдельных ключей.** `ForceCommand` в `sshd_config` их переопределяет. Права для каждого ключа задаются через §3.3.
- `ExposeAuthInfo` заставляет sshd записать открытый ключ, которым прошла аутентификация, в файл, путь к которому лежит в `$SSH_USER_AUTH`. Клиент не может задать или изменить эту переменную (`PermitUserEnvironment no`; её никогда нет в `AcceptEnv`).
- passh игнорирует всё унаследованное окружение, кроме переменных `SSH_*`, которые он читает, и `TERM`, которую он проверяет. Поэтому настройки дистрибутива по умолчанию, такие как `AcceptEnv LANG LC_*`, безвредны.
- `sshd` слушает только на интерфейсе VPN (`ListenAddress`), либо межсетевой экран отбрасывает трафик на порт 22 на всех остальных интерфейсах.

### 3.3 Политика хоста (`/etc/passh/policy.toml`)

Принадлежит root (root:root 0644). Содержит права для каждого ключа и функции уровня хоста, например страницу печати (§7.4). passh сопоставляет ключ из `$SSH_USER_AUTH` с его правами. **Неизвестные ключи отклоняются.**

```toml
[[key]]
name         = "laptop"
fingerprint  = "SHA256:…"      # as printed by ssh-keygen -lf
access       = "read-write"
batch        = true
export       = "encrypted"
fresh_unlock = false

[[key]]
name         = "phone"
fingerprint  = "SHA256:…"
# defaults: read-only, no batch, no export, fresh_unlock

[print_web]                     # §7.4; off unless enabled here
enabled    = false
port       = 8443
interfaces = ["wg0", "eth0"]    # only private addresses on these are used
allow_from = []                 # extra CIDR limit; default = subnets of the bound addresses
hostnames  = ["pi.local"]       # optional names for the certificate
ttl        = "5m"               # 1–15 min
```

| Поле | Значения | По умолчанию | Назначение |
|---|---|---|---|
| `name` | текст | обязательно | Показывается в заголовке TUI и в журнале аудита |
| `fingerprint` | `SHA256:…` | обязательно | Отпечаток ключа |
| `access` | `read-only` / `read-write` | `read-only` | Разрешены ли команды записи (§6.1) |
| `batch` | bool | `false` | Могут ли неинтерактивные команды (без PTY) расшифровывать или подписывать, например `ssh pi show x \| pbcopy` |
| `export` | `none` / `encrypted` / `plaintext` | `none` | Права на массовый экспорт, печать и страницу печати (§7) |
| `fresh_unlock` | bool | `true` | Новая интерактивная сессия с этого ключа сбрасывает кеш агента перед первой расшифровкой, поэтому никогда не пользуется разблокировкой, сделанной с другого устройства (§5.1). Это также блокирует другие открытые сессии |

- Неинтерактивные команды не могут запросить ввод. Поэтому ключ с `fresh_unlock = true` не может использовать `batch` или экспорт с расшифровкой; passh отклоняет такие сочетания при загрузке файла.
- Сессия отклоняется, если `policy.toml` отсутствует, не читается, не принадлежит root или некорректен, а также если `$SSH_USER_AUTH` указывает не ровно на один `publickey`.

### 3.4 Режимы

| Режим | Как войти | Что разрешено |
|---|---|---|
| **SSH** (ограниченный) | Любая сессия, запущенная sshd; определяется по любой переменной `SSH_*` (`SSH_CONNECTION`, `SSH_CLIENT`, `SSH_TTY`, `SSH_ORIGINAL_COMMAND`, `SSH_USER_AUTH`) | Команды из §6.1, разрешённые политикой ключа (§3.3). Только встроенный редактор. passh напрямую запускает только `gpg`, `gpg-connect-agent` и `git` с фиксированными аргументами и не открывает сетевых слушателей, кроме страницы печати (§7.4) |
| **Консольный** (ограниченный) | `passh`, запущенный локально от имени `vault` без `--admin` | Тот же набор команд, что и по SSH, с правами на чтение и запись и всеми возможностями |
| **Административный** | `passh --admin …` | Все команды, включая `init`, `restore`, `recipients set`, `key backup`, `verify --accept`, `print --recovery-kit`, экспорт в файл и внешний `$EDITOR` (§5.4) |

- Ограниченный режим используется по умолчанию; флага, который его отключает, нет — есть только `--admin`, чтобы явно перейти в административный режим.
- `--admin` отклоняется, если задана любая переменная `SSH_*` или stdin не является TTY. Никакой флаг в `SSH_ORIGINAL_COMMAND` не может изменить режим или политику (§6.4).
- **Административный путь:** войдите по SSH как обычный пользователь с правами sudo, затем выполните `sudo machinectl shell vault@`. Так `vault` получает собственную сессию входа и TTY, и pinentry может открыть терминал. `sudo -u vault` не подходит: TTY остаётся во владении администратора, и pinentry не может его открыть. В контейнере вместо этого используется `docker exec` (§3.5).

### 3.5 Развёртывание в контейнере (Docker)

passh можно запускать в контейнере Docker, а не прямо на хосте. Действуют §3.1–3.4 со следующими отличиями.

**Образ и контейнер**

- Один контейнер запускает sshd и passh. На хосте остаётся собственный sshd для администратора.
- Образ: Debian bookworm-slim с `gnupg`, `git`, `openssh-server`, `openssh-client` и `pinentry-curses`, а также passh, принадлежащий root. Образ загружается по digest; digest указан в подписанных примечаниях к выпуску (§10.1).
- **Сеть хоста.** Действует межсетевой экран хоста, а страница печати видит настоящие адреса хоста (§7.4). sshd слушает адреса из `SSH_LISTEN`, по умолчанию порт 2222; точка входа передаёт их sshd через `-o ListenAddress=…`.
- **Сеть bridge в v1 не поддерживается.** Публикация портов в Docker обходит межсетевые экраны хоста, такие как ufw, а страница печати видела бы адреса контейнера вместо адресов хоста.
- sshd использует настройки из §3.2, а также `AllowUsers vault`, `PermitRootLogin no`, `AuthorizedKeysFile /etc/passh/authorized_keys` и ключи хоста в `/etc/ssh/keys`. Точка входа создаёт недостающие ключи хоста.
- У `vault` UID 10001 и оболочка входа `/bin/sh`. Его домашний каталог принадлежит root, а подкаталоги — `vault`; точка входа проверяет это при каждом запуске.

**Усиление защиты**

- Корневая файловая система только для чтения. tmpfs для `/tmp` и для `/run/sshd` с режимом 0755 (sshd отказывается работать с каталогом разделения привилегий, доступным на запись всем). `/dev/shm` — tmpfs (R1).
- `cap_drop: ALL`, обратно добавляется только то, что нужно sshd: `CHOWN`, `SETUID`, `SETGID`, `SYS_CHROOT`, `KILL`, `AUDIT_WRITE`. `no-new-privileges`. CI проверяет, что вход работает ровно с этим набором.
- **Swap:** `memswap_limit` равен `mem_limit`, поэтому контейнер не может использовать подкачку. passh проверяет это, читая `memory.swap.max` в cgroup, потому что на ядрах без учёта swap Docker молча игнорирует лимит. Если значение не 0, действует правило хоста из §3.1: никакого swap на диске.
- ulimit `memlock` 64 МиБ для заблокированных в памяти секретов (R3); ulimit `core` 0 (R2).
- Часы берутся с хоста, поэтому синхронизация времени работает на хосте (§3.1).
- **Журнал аудита:** сокет журнала хоста монтируется в контейнер. Без него passh дописывает записи в `<state>/audit.log`, а `doctor` предупреждает об этом.

**Административный путь**

- `docker exec -it -u vault passh …` заменяет `machinectl` (§3.4). Он не задаёт переменных `SSH_*` и даёт TTY, поэтому `--admin` работает, а pinentry может открыть терминал.
- Любой, кто может запускать `docker` на хосте, по сути равен root и поэтому является администратором passh.

**Папки** (пути на хосте приведены для примера)

| Папка на хосте | В контейнере | Что содержит | Резервировать? |
|---|---|---|---|
| `/srv/passh/backup/config/` | `/etc/passh` (только чтение) | `policy.toml`, `authorized_keys` | **Да** |
| `/srv/passh/backup/store/` | `/home/vault/.password-store` | Хранилище, включая обёрнутый ключ (§8.2) | **Да** |
| `/srv/passh/local/home/` | `/home/vault` | Связка ключей GnuPG и сокеты агента, `pins.toml`, состояние, ключ push, CA страницы печати | **Нет** |
| `/srv/passh/local/ssh-host-keys/` | `/etc/ssh/keys` | SSH-ключи хоста контейнера | **Нет** |

- В `backup/` лежат только открытые данные или данные, защищённые парольной фразой. Для восстановления достаточно резервной копии этой одной папки (§8.4).
- `local/` никогда не резервируется. В ней лежат:
  - копия ключа в GnuPG, защищённая слабее, чем копия, обёрнутая age;
  - SSH-ключи хоста. Имея резервную копию и эти ключи, атакующий мог бы выдать себя за сервер и перехватить парольную фразу;
  - ключ push и ключ CA страницы печати.

  Восстановление заново создаёт `local/`. После этого клиенты увидят новый ключ хоста, а CA страницы печати нужно создать и установить заново.
- `backup/` можно копировать, пока passh работает. Копия, снятая посреди записи, не пройдёт проверку при восстановлении и исправляется через `verify --discard` (§4.5).

## 4. Формат хранения и целостность

### 4.1 Структура (совместимая с pass)

```
~/.password-store/
├── .gpg-id                   # recipient key fingerprint(s), root of the store only
├── .gpg-id.sig               # detached signature of .gpg-id (pass-compatible)
├── .git/
├── .passh/                   # passh-specific data; ignored by pass
│   ├── config.toml
│   ├── tags.idx.gpg          # encrypted tag index (§4.3)
│   ├── pubkey.asc            # public key, armored
│   └── secret-key.asc.age    # passphrase-protected secret key (§8.2)
├── work/
│   ├── jira.gpg
│   └── github.gpg
└── bank/
    └── revolut.gpg
```

Локальное состояние вне репозитория (никогда не отправляется через push):

- `~/.config/passh/pins.toml`: закреплённые получатели, ключ подписи и получатели экспорта (§4.4, §7.1). Записывается только в административном режиме.
- `~/.local/state/passh/`: `verified-head` (§4.5), файл блокировки хранилища `lock` (§4.7), счётчик неудачных разблокировок (§5.1), статус последнего push (§8.3) и `known_hosts` для резервных репозиториев.

`.passh/config.toml` содержит настройки, такие как `session.*`, `clipboard.*` и `backup.remotes`. Меняйте его только через `passh --admin config set` или `remote add/remove`: эти команды проверяют значение и создают подписанный коммит. Ручная правка файла оставляет рабочее дерево «грязным», и проверка не проходит (§4.5).

- **Папки = категории.** Это родная модель pass, и она остаётся основной иерархией.
- Имена файлов и пути **не шифруются**. Кроме того, история git навсегда хранит имена удалённых записей и их старые шифротексты. Оба риска приняты (§9).

### 4.2 Формат записи

Как в соглашении pass. Строка 1 — пароль, за ней метаданные `key: value`, затем заметки в свободной форме.

```
s3cr3t-P@ss
username: arsenii
url: https://github.com
tags: work, dev, 2fa
---
Free-form notes. Recovery codes, etc.
```

- Метаданные — это идущие подряд строки `key: value` (ключ соответствует `[a-z0-9_-]+`) сразу после строки 1. Они заканчиваются на строке `---` или на первой строке, которая не подходит под этот формат. Всё, что дальше, — заметки. `---` — соглашение passh; pass считает весь файл текстом в свободной форме.
- Зарезервированные ключи: `username`, `url`, `tags`, `otp` (зарезервирован для будущей версии, в v1 не реализован).
- Значения `otp:` и строки `otpauth://` (формат pass-otp) считаются секретами: маскируются, никогда не индексируются, экспортируются отдельным полем.
- Неизвестные и повторяющиеся ключи сохраняются в исходном порядке; показывается первый из них.
- Запись, которую passh только читает, никогда не перезаписывается. При редактировании перезаписываются только изменённые строки.
- Поля формы, кроме заметок, не принимают переводы строк. Иначе через имя пользователя можно было бы внедрить строки `tags:` или `url:`.

### 4.3 Теги

Теги хранятся внутри зашифрованной записи, поэтому для вывода списка по тегу пришлось бы расшифровать каждый файл. Чтобы этого избежать:

- passh ведёт `.passh/tags.idx.gpg` — зашифрованную карту `{path → [tags]}`. Она зашифрована для тех же закреплённых получателей, что и хранилище.
- Индекс расшифровывается один раз после разблокировки и хранится в памяти до конца сессии.
- Он обновляется в том же коммите, что и каждое добавление, правка, перемещение или удаление, сделанные через passh.
- `passh reindex` перестраивает его, расшифровывая все записи по одной. Используйте эту команду после правок через обычный `pass` или вручную, а также если файл отсутствует.
- Индекс хранит хеш отсортированного списка `(path, git blob id)` всех записей. Если хеш не совпадает с текущим хранилищем, TUI показывает «tag index stale — run reindex». Хеш коммита использовать нельзя: индекс попадает в тот самый коммит, на который ему пришлось бы ссылаться.

Решение: теги **дополняют** папки, а не заменяют их. Папки остаются ради совместимости с pass. Теги нужны для сквозных представлений, таких как `2fa`, `shared-with-family` или `rotate-soon`.

### 4.4 Закрепление получателей (защита `.gpg-id`)

Угроза: любой, кто может писать в хранилище, может подменить `.gpg-id`, чтобы новые записи шифровались ключом атакующего.

- `~/.config/passh/pins.toml` (вне репозитория, записывается только в административном режиме) закрепляет ожидаемые отпечатки. Отпечатки всегда указываются полностью, 40 символов, и никогда не в виде коротких ID ключей:
  ```toml
  [crypto]
  recipients  = ["0123456789ABCDEF0123456789ABCDEF01234567"]
  signing_key = "0123456789ABCDEF0123456789ABCDEF01234567"
  ```
  Копия хранится в `.passh/config.toml`, чтобы закреплённые значения попадали в резервные копии. Обе копии должны совпадать. При восстановлении якорем доверия служит отпечаток, который вводит пользователь (§8.4), а не склонированный `config.toml`.
- `.gpg-id.sig` — отсоединённая подпись ключом `signing_key`; это тот же механизм, что и `PASSWORD_STORE_SIGNING_KEY` в pass. pass проверяет её, только если эта переменная задана, поэтому README советует администраторам задать её для обычного `pass`.
- **Перед каждым шифрованием** passh проверяет `.gpg-id.sig` и то, что `.gpg-id` в точности совпадает с закреплёнными получателями. При любом несовпадении он отказывается писать и показывает ошибку целостности.
- **Допускается только корневой `.gpg-id`.** pass учитывает файлы `.gpg-id` в подпапках и шифровал бы такую папку для других ключей. Любой `.gpg-id` ниже корня — ошибка целостности, а `init --adopt` отказывается принимать хранилище с таким файлом и объясняет администратору, как выполнить слияние.
- `.gpg-id` должен содержать полные отпечатки. Если в `.gpg-id` принимаемого хранилища указаны адреса электронной почты или короткие ID, `init --adopt` перезаписывает его после подтверждения.
- Для смены получателей нужна команда `passh recipients set …` в административном режиме. Она заново подписывает `.gpg-id`, перешифровывает все записи и индекс, обновляет `.passh/pubkey.asc` и `secret-key.asc.age` и делает коммит.
- **Перешифрование не отзывает доступ.** Старые шифротексты остаются в истории git и в репозитории только на добавление (append-only), и старый ключ по-прежнему их читает. После компрометации ключа смените все пароли. passh напоминает об этом после `recipients set`.
- При принятии существующего хранилища pass команда `init --adopt` показывает текущий `.gpg-id` для подтверждения, затем создаёт подпись, закрепления, резервную копию ключа (§8.2) и подписанный коммит принятия (§4.5).

### 4.5 Целостность истории (подписанные коммиты)

Угроза: шифрование GPG не подтверждает, кто автор записи. Атакующий может подложить корректно зашифрованную запись, например заменить URL банка на фишинговый.

**Подпись.** Каждый коммит, созданный passh, подписывается ключом `signing_key`. passh собирает коммиты plumbing-командами git, поэтому сам запускает gpg по правилам §5.5 и никогда не полагается на `gpg.program`:

1. добавить изменения в индекс через `git update-index`;
2. `git write-tree`;
3. подписать содержимое коммита через gpg отсоединённой подписью;
4. `git hash-object -t commit -w --stdin`;
5. `git update-ref HEAD <new> <old>`; если HEAD сдвинулся, операция сравнения с обменом (compare-and-swap) завершается явной ошибкой.

Для подписи нужен разблокированный ключ, поэтому запись возможна только в разблокированной сессии.

**Проверка.** passh проверяет подписи сам:

- Он читает коммит через `git cat-file commit`, отделяет заголовок `gpgsig` от подписанного содержимого и запускает `gpg --verify` со статусом на fd 3.
- Коммит считается **подписанным**, если у него ровно одна подпись и отпечаток *основного ключа* из `VALIDSIG` (последнее поле; первое — подключ) равен закреплённому `signing_key`.
- Подписи ключом с истёкшим сроком действия (`EXPKEYSIG`) принимаются с предупреждением, а запись блокируется, пока срок действия ключа не продлят. `REVKEYSIG`, `BADSIG`, `ERRSIG`, любой другой ключ и несколько подписей означают, что коммит не подписан.

**Правило доверия.** Подписанный коммит ручается за своё дерево и, через цепочку хешей git, за всех своих предков. passh **никогда не создаёт подписанный коммит, если хранилище не проверено**, и именно это делает правило надёжным. Хранилище считается **проверенным**, когда выполнены все условия:

1. HEAD подписан;
2. `verified-head`, если он есть, является предком HEAD, то есть история не переписывалась;
3. рабочее дерево, индекс и HEAD идентичны: `git status --porcelain --untracked-files=all --ignored` ничего не выводит.

Проверка выполняется при запуске и перед каждой записью. При успехе `verified-head` продвигается до HEAD. Если `verified-head` отсутствует (новый хост, потерянное состояние), действуют правила 1 и 3, а TUI один раз показывает дату вершины и число записей для подтверждения.

**При неудаче:**

- запись запрещена;
- чтение продолжается, но TUI показывает красный баннер целостности со списком коммитов после последнего подписанного и путей, которые они изменили (с очисткой вывода, R8);
- неподписанные коммиты сверху (например, сделанные обычным `pass`): администратор просматривает их и принимает командой `passh --admin verify --accept <commit>`. `<commit>` должен быть HEAD и указываться полным шестнадцатеричным id. Команда требует разблокировки и создаёт **подписанный пустой коммит** «passh: accept <ids>», который ручается за них во всех клонах, включая восстановленные;
- грязное рабочее дерево: администратор устраняет это командой `passh --admin verify --discard`, которая сбрасывает состояние до HEAD, предварительно показав, что будет потеряно, либо делает коммит через passh.

**Чтобы обычный `pass` тоже подписывал.** При принятии в локальной конфигурации репозитория задаются `commit.gpgsign = true` и `user.signingkey = <fpr>` (оба ключа есть в списке разрешённых, §5.5). Тогда обычный `pass`, которым администратор пользуется на сервере, создаёт подписанные коммиты, и `verify --accept` требуется редко.

**Принятие и ротация ключа.** Коммит принятия подписан, поэтому он ручается за неподписанную историю хранилища до принятия. После смены ключа новые коммиты подписываются новым ключом, а при восстановлении используется новый отпечаток; по правилу доверия старые подписи значения не имеют.

passh не подписывает отдельные записи: их покрывают подписи коммитов.

### 4.6 Правила для путей

Каждый путь, полученный от пользователя или прочитанный с диска, проходит через единый валидатор, который выдаёт `paths.Safe` (§10.3). Правила отклоняют только опасное, поэтому существующие хранилища pass открываются без изменений:

- путь относителен к корню хранилища, нормализован (`filepath.Clean`), без пустых сегментов, `.` и `..`, без абсолютных путей, без `\`;
- **ни один сегмент не начинается с `.`** (это покрывает `.git`, `.passh`, `.gpg-id`, `.gitattributes`, `.gitmodules` и `.extensions` из pass на любой глубине);
- **ни один сегмент не начинается с `-`**;
- без управляющих символов (C0, C1, DEL), без NUL, без символов форматирования Unicode (категория Cf: переопределения направления текста bidi, символы нулевой ширины);
- всё остальное разрешено, включая пробелы, `& ' ( ) , : # =` и комбинируемые знаки. Это безопасно, потому что ничто не запускает shell, перед каждым аргументом-путём стоит `--`, а git работает с `GIT_LITERAL_PATHSPECS=1` (§5.5);
- поиск не зависит от нормализации NFC; новые имена записываются в NFC.

Открытие файлов:

- Весь доступ к файлам идёт через `os.Root` (Go ≥ 1.24), привязанный к корню хранилища, плюс `Lstat` для каждого компонента пути, который **отклоняет символические ссылки**.
- git работает с `core.symlinks=false`, поэтому сам git никогда не создаёт символические ссылки в рабочем дереве; закоммиченная символическая ссылка извлекается как обычный файл.

Имя на диске, не прошедшее проверку, показывается в списке (после очистки вывода) с предупреждением, и его нельзя открыть, пока администратор его не переименует.

### 4.7 Параллельный доступ и атомарная запись

- Каждая последовательность записи (проверка → шифрование → запись → индекс → коммит) удерживает эксклюзивный `flock` на `~/.local/state/passh/lock`. Читатели блокировку не берут.
- Данные пишутся во временный файл в том же каталоге, сбрасываются на диск через `fsync` и переименовываются. Коммит делается до снятия блокировки, поэтому при нормальной работе дерево никогда не остаётся грязным. После сбоя грязное дерево не проходит правило 3 (§4.5), и администратор разбирается с ним.
- Сессии, которые держат индекс тегов в памяти, перед каждой записью перепроверяют его хеш и перезагружают индекс, если другая сессия изменила хранилище.

## 5. Модель сессий и безопасности

### 5.1 Разблокировка

- Расшифровка делегируется системному бинарному файлу `gpg` (см. ADR-1).
- **Pinentry:** первая операция, которой нужен секрет, вызывает запрос через принадлежащий root системный `pinentry-curses` или `pinentry-tty`. passh передаёт собственный `GPG_TTY` и проверенный `TERM` в каждый вызов gpg; gpg пересылает оба значения агенту для этого запроса. `updatestartuptty` не нужен: он влияет только на поддержку ssh в агенте.
- **Разблокировка подготавливает оба ключа.** Она расшифровывает индекс тегов и создаёт одноразовую отсоединённую подпись, поэтому запросы для ключей расшифровки и подписи появляются при разблокировке, а не посреди записи.
- **Нет TTY** (неинтерактивная команда): каждый вызов gpg получает `--pinentry-mode error`. Если ключа нет в кеше, команда завершается ошибкой «unlock in an interactive session first», а не выводит запрос где-то ещё. Перед подписью passh проверяет keygrip ключа подписи через `KEYINFO`.
- **Передача терминала:** перед любым вызовом gpg, который может запросить ввод, TUI освобождает терминал (выходит из альтернативного экрана, возвращает канонический режим, перестаёт читать ввод), а затем забирает его обратно. passh никогда не читает нажатия клавиш, пока может быть активен pinentry, поэтому символы парольной фразы не попадут в поле поиска и не вызовут действий.
- **Свежая разблокировка:** если в политике ключа `fresh_unlock = true`, новая интерактивная сессия с этого ключа сбрасывает кеш агента перед первой расшифровкой (§3.3).
- **Задержка после неудачных разблокировок:** passh считает вызовы gpg, завершившиеся ошибкой неверной парольной фразы, по всем сессиям, в своём каталоге состояния. После 3 неудач за 15 минут разблокировка запрещается на экспоненциально растущее время (1, 2, 4 … до 60 минут). Каждая неудача записывается в журнал с именем ключа.
- Разблокированный ключ кеширует **gpg-agent** со следующими TTL:

| Параметр | По умолчанию | Ключ конфигурации |
|---|---|---|
| TTL простоя (с последнего использования) | 5 мин | `session.idle_ttl` |
| Максимальный TTL (с момента разблокировки) | 15 мин | `session.max_ttl` |

**Проверка `gpg-agent.conf`.** `passh init` записывает этот файл, а passh проверяет его **при каждом запуске** и отказывается расшифровывать, если проверка не прошла. Пользователь `vault` может переписать этот файл, поэтому от самого этого пользователя проверка не защищает (§9). Файл сверяется со списком разрешённых директив:

- `default-cache-ttl` и `max-cache-ttl` не больше настроенных TTL. Отсутствие строки означает значения gpg по умолчанию (600 с / 7200 с), и проверка не проходит;
- `pinentry-program` указывает на принадлежащий root системный pinentry;
- присутствуют `no-allow-loopback-pinentry` и `no-allow-external-cache`. В gpg-agent loopback **разрешён по умолчанию**, поэтому отсутствие `allow-loopback-pinentry` ничего не доказывает;
- `allow-preset-passphrase` или любая директива не из списка разрешённых проваливают проверку.

Если файл изменился после запуска агента, passh перед использованием выполняет `gpg-connect-agent reloadagent /bye`.

### 5.2 Блокировка и сигналы

Кеш агента сбрасывается (`gpg-connect-agent reloadagent /bye`), индекс тегов в памяти и все расшифрованные записи затираются, а TUI показывает экран блокировки, когда происходит любое из следующего:

- пользователь нажимает `L` в TUI или выполняет `passh lock`;
- TUI штатно завершается;
- получен SIGHUP, SIGTERM, SIGINT или SIGQUIT (разрыв SSH-соединения);
- TUI простаивает в течение `session.idle_ttl`.

Блокировка также останавливает сервер страницы печати (§7.4).

Сигналы и сбои:

- SIGPIPE игнорируется, поэтому запись в закрытый конвейер завершается ошибкой EPIPE, и passh выходит через обычную процедуру очистки. По умолчанию Go сразу завершил бы процесс при такой ошибке на fd 1 или 2.
- При запуске устанавливается `GOTRACEBACK=none`. Recover на верхнем уровне затирает секреты перед выходом.
- При запуске passh удаляет устаревшие временные каталоги, оставшиеся после аварийного завершения.
- Неинтерактивные команды не выполняют блокировку при выходе; они полагаются на разблокировку, сделанную в другом месте.

Известное ограничение: gpg-agent один на пользователя Unix, а не на SSH-сессию. Блокировка в одной сессии блокирует все, и так задумано. Заголовок TUI показывает имя ключа и число других активных сессий passh, поэтому неожиданная сессия будет заметна. Если passh убит через SIGKILL, он не может сбросить кеш; тогда последний рубеж — собственные TTL агента.

### 5.3 Правила работы с секретами

| Правило | Подробности |
|---|---|
| R1 | Никогда не записывать открытый текст на постоянный диск. umask 077 при запуске. Временные файлы — только в административном режиме (`$EDITOR`, `export -o`), только на tmpfs (проверяется через `statfs`, а не по пути), с правами 0600, в каталоге 0700; удаляются при выходе и по сигналу. Ограниченные режимы не создают временных файлов с открытым текстом |
| R2 | Дампы памяти отключаются при запуске (`setrlimit RLIMIT_CORE 0`), устанавливается `prctl(PR_SET_DUMPABLE, 0)` (не наследуется через exec), `GOTRACEBACK=none` |
| R3 | Секреты хранятся в буферах `[]byte`, выделенных вне кучи Go и закреплённых в RAM через `mlock` (`awnumar/memguard`), и обнуляются после использования. Массовые операции (reindex, экспорт) обрабатывают записи по одной, чтобы не выйти за `RLIMIT_MEMLOCK`; `doctor` проверяет этот лимит. Данные, которые проходят через строки Go (отрисовка TUI, кодировщики JSON/CSV/PDF), — задокументированное ограничение; последний рубеж — требование к swap (§3.1) |
| R4 | Пароли в TUI по умолчанию скрыты маской фиксированной длины, которая не раскрывает длину пароля. Показываются только по явному действию и снова скрываются через 10 с |
| R5 | Никаких секретов в журналах, сообщениях об ошибках и сообщениях коммитов git. Сообщения коммитов содержат только действие и путь |
| R6 | Буфер обмена: passh отправляет очищающую последовательность OSC 52 через `clipboard.clear_after` (по умолчанию 30 с). Он **не может проверить**, что лежит в буфере обмена, а если сессия завершится раньше, очистка не произойдёт. Оба ограничения задокументированы и показываются в `passh help copy` |
| R7 | Экспорт открытого текста, печать и страница печати требуют явного права и подтверждения (§7) |
| R8 | **Очистка вывода.** Всё, что passh выводит для людей (TUI, stdout и stderr, во всех режимах, **включая конвейеры**), проходит очистку. Управляющие символы C0, кроме перевода строки и табуляции, а также C1, DEL, escape-последовательности и символы форматирования Unicode (bidi, нулевой ширины) показываются экранированными, в виде `\x1b`/`\u202e`. Сервер не может знать, заканчивается ли конвейер в терминале клиента, поэтому для конвейеров исключения нет. `show --raw` выводит байты как есть; эта команда отклоняется, если stdout — терминал, и требует `batch` у ключа. Вывод git и gpg никогда не пересылается; passh печатает собственные сообщения. Потоки данных экспорта и печати подчиняются §7. Страница печати экранирует каждое значение для HTML и применяет те же экранирования (§7.4) |
| R9 | **Генерация паролей** использует `crypto/rand` с отбраковкой (rejection sampling, без смещения от взятия по модулю). Длина по умолчанию 24, алфавит настраивается. Генерация завершается ошибкой, а не переходит на более слабый источник. Тот же генератор создаёт парольную фразу из 6 слов, которую предлагает `init` (§8.2) |
| R10 | Открытый текст передаётся в `gpg --encrypt` через stdin и никогда — как аргумент командной строки или переменная окружения |

### 5.4 Редактирование

- **Ограниченные режимы:** редактирование выполняется во встроенной форме TUI (`bubbles/textarea` для заметок, отдельные однострочные поля для пароля, имени пользователя, url и тегов). Внешний редактор не запускается никогда. `passh edit <path>` открывает ту же форму.
- **Административный режим:** `passh --admin edit --editor <path>` использует `$EDITOR`, временный файл размещается на tmpfs (R1). `$EDITOR` разбивается на слова без shell. Защита от утечек (каждый флаг передаётся отдельным аргументом):
  - vim: `-n -u NONE -i NONE -c "set nobackup nowritebackup noundofile noswapfile"`;
  - neovim: `-n --clean -i NONE -c "set nobackup nowritebackup noundofile noswapfile"`;
  - nano: `--ignorercfiles --nohelp` (nano не делает резервных копий, если его об этом не просить);
  - любой другой редактор: passh предупреждает, что не может контролировать файлы резервных копий и подкачки, и просит подтверждения.
- Пейджер не используется никогда. Длинный вывод прокручивается внутри TUI.

### 5.5 Правила для подпроцессов

Все внешние команды запускаются через единственный пакет `internal/exec`.

**Фиксированные бинарные файлы, без shell:**

- Бинарные файлы вызываются по абсолютному пути, который задаётся один раз и проверяется `doctor`, и никогда не ищутся через `$PATH`:
  - ограниченные режимы: `/usr/bin/gpg`, `/usr/bin/gpg-connect-agent`, `/usr/bin/git`;
  - административный режим добавляет `$EDITOR` и `/usr/bin/lp`.
- Эти программы запускают собственных помощников, и те тоже закреплены: gpg запускает gpg-agent и закреплённый pinentry; git для push запускает `/bin/sh` и `/usr/bin/ssh` через фиксированный `GIT_SSH_COMMAND`. Тесты проверяют прямых потомков и эти закрепления.
- Никакого shell. Только `exec.Command` со списком аргументов.
- `--` перед каждым аргументом-путём, в дополнение к правилам для путей (§4.6).

**Чистое окружение во всех режимах.** Подпроцессы получают только:

- `PATH=/usr/bin:/bin`;
- `HOME` и `GNUPGHOME`, взятые из записи passwd и конфигурации, а не унаследованные;
- `GPG_TTY` и `TERM`, проверенный по `^[A-Za-z0-9._+-]{1,64}$`;
- `LANG=C.UTF-8`;
- `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_TERMINAL_PROMPT=0`, `GIT_LITERAL_PATHSPECS=1`;
- `GIT_SSH_COMMAND=/usr/bin/ssh -F /dev/null -o BatchMode=yes -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes -o UserKnownHostsFile=<state>/known_hosts -i <push key>`. git выполняет его через `/bin/sh`, поэтому passh собирает эту строку только из фиксированных проверенных путей без пробелов и символов shell.

**Усиление защиты git.** Каждый вызов получает:

```
--no-pager -c core.hooksPath=/dev/null -c core.pager=cat -c core.fsmonitor=false
-c core.symlinks=false -c protocol.allow=never -c protocol.ssh.allow=always
-c transfer.fsckObjects=true -c submodule.recurse=false -c gc.auto=0
```

- **Список разрешённых ключей в `.git/config` репозитория** проверяется при каждом запуске, а не только `doctor`. Разрешены ключи:
  - `core.repositoryformatversion`, `core.filemode`, `core.bare` (false), `core.logallrefupdates`;
  - `remote.<name>.url` и `remote.<name>.fetch`, `branch.<name>.remote` и `branch.<name>.merge`;
  - `commit.gpgsign` и `user.signingkey` (должен совпадать с закреплённым значением);
  - `diff.gpg.binary` и `diff.gpg.textconv`, только с теми точными значениями, которые записывает `pass git init`.

  Любой другой ключ, например `gpg.program`, `core.sshCommand`, `core.editor`, `filter.*`, `include*`, `url.*.insteadOf`, `remote.*.uploadpack` или `diff.external`, — ошибка целостности, и passh не запускает ни одной команды git, пока администратор его не удалит. passh никогда не запускает команды git, которые используют textconv или внешний diff.
- **URL удалённых репозиториев:** только `ssh://…` или `user@host:path`, причём хост и путь не могут начинаться с `-`. Проверяется перед каждым push.
- **ID коммитов**, полученные от пользователей (например, в `verify --accept`), должны быть полными шестнадцатеричными id.

**Вызовы gpg:**

- Каждый вызов получает `--no-options --homedir <GNUPGHOME> --batch --no-tty --status-fd 3`, а если TTY нет — ещё и `--pinentry-mode error`. `--no-options` пропускает `gpg.conf`, поэтому `encrypt-to`, `group`, `default-recipient` или автоматическое получение ключей, заданные там, не могут изменить поведение.
- Вывод разбирается только из машиночитаемых строк статуса на **fd 3** — отдельном канале. Никогда из человекочитаемого stderr и никогда из fd 1 или 2, где открытый текст или stderr могли бы подделать строки `[GNUPG:]`. Это исключает класс ошибок, стоящий за CVE-2018-12356 в pass.
- **Шифрование:** `--encrypt --trust-model always --no-encrypt-to`, по одному `--recipient <full fpr>` на каждого закреплённого получателя.
- **Расшифровка:** требуются `DECRYPTION_OKAY` и `END_DECRYPTION` и отсутствие `DECRYPTION_FAILED` или `BADMDC`. Незашифрованный файл (literal-данные или данные только с подписью) отклоняется. `--max-output` ограничивает размер открытого текста (1 МиБ на запись, 64 МиБ для индекса).
- **Проверка подписи:** см. §4.5.

### 6.1 CLI

Запуск `passh` без аргументов открывает TUI.

|---|---|---|---|---|
| `passh` (TUI) | — | ✓ просмотр и чтение | ✓ | ✓ |
| `ls [folder]`, `find <query>` по путям | meta | ✓ | ✓ | ✓ |
| `ls --tag t`, `find` с учётом тегов, `tags` | read | ✓ | ✓ | ✓ |
| `show <path> [--field f] [--raw]` | read | ✓ | ✓ | ✓ |
| `copy <path> [--field f]` | read | ✓ | ✓ | ✓ |
| `add <path> [--force]`, `generate <path> [len] [--symbols] [--force]` | write | ✗ | ✓ | ✓ |
| `edit <path>` (встроенная форма) | write | ✗ | ✓ | ✓ |
| `mv <src> <dst>`, `rm <path>` | write | ✗ | ✓ | ✓ |
| `tag <path> --add a --remove b`, `reindex` | write | ✗ | ✓ | ✓ |

| `print --recovery-kit`, `export -o <file>`, `print --lp <printer>`, `edit --editor` | admin | ✗ | ✗ | ✓ |

Правила:

- **Неинтерактивные** (без PTY) команды классов `read` и `write`, а также команды `bulk` с расшифровкой требуют у ключа `batch = true`. Командам `meta` это не нужно.
- **Запрет по умолчанию.** Команды, подкоманды и флаги, которых нет в этой таблице, отклоняются. Команда `completion` из Cobra и сопоставление команд по префиксу отключены. Тест обходит дерево команд cobra и сверяет каждую команду и каждый флаг с таблицей.
- Клавиши TUI подчиняются той же матрице: ключ только для чтения не видит `e`, `a`, `t` и `d`.
- `add` и `generate` для уже существующего пути без `--force` отклоняются; TUI вместо этого запрашивает подтверждение.
- Вывод `show` проходит очистку (R8); `--raw` нужен, чтобы передать в конвейер точные байты.

**Проброса команд в git нет.** Произвольные команды git администратор выполняет обычным `git`.

### 6.2 TUI

Построен на Bubble Tea + Bubbles + Lip Gloss (charmbracelet).

```
┌ passh ── 🔓 unlocked · locks in 4:12 · ✔ verified · laptop +1 ───┐
│ VIEW: [Folders]  Tags                     / search_              │
├──────────────────────┬───────────────────────────────────────────┤
│ ▸ bank          (3)  │ work/github                               │
│ ▾ work          (12) │ username  arsenii                         │
│     github           │ password  ••••••••       [c]opy [r]eveal  │
│     jira             │ url       https://github.com              │
│     confluence       │ tags      work · dev · 2fa                │
│ ▸ homelab       (7)  │ notes     Recovery codes in notes…        │
├──────────────────────┴───────────────────────────────────────────┤
│ c copy pw · u copy user · r reveal · e edit · a add · t tags     │
│ Tab folders/tags · / search · L lock · ? help · q quit           │
└──────────────────────────────────────────────────────────────────┘
```

Требования:

- **Два представления**, переключаются клавишей `Tab`:
  - *Folders* (папки): сворачиваемое дерево, которое повторяет структуру каталогов;
  - *Tags* (теги): список тегов с количеством записей; выбор тега показывает его записи. Можно выбрать несколько тегов (логическое И).
- `/` открывает нечёткий поиск по пути и тегам (из индекса). Имена пользователей и URL не индексируются, поэтому поиск по ним потребовал бы расшифровки каждой записи.
- Панель подробностей расшифровывает только выбранную запись, в момент выбора (с задержкой 150 мс) и только в разблокированном состоянии. В заблокированном состоянии она показывает только путь (теги берутся из зашифрованного индекса).
- **Заголовок:** состояние блокировки и обратный отсчёт; состояние целостности (`✔ verified` или красный баннер `⚠ integrity`, §4.5); имя текущего ключа; число других активных сессий; предупреждение, если последний push не удался или был больше суток назад (§8.3); и `🖨 print page 4:12`, пока работает страница печати (§7.4).
- `P` открывает диалог страницы печати (§7.4) для ключей, которым она разрешена.
- Все отображаемые значения проходят очистку (R8). Запросы gpg используют передачу терминала (§5.1).
- Узкие терминалы (меньше 80 столбцов, например на телефонах) работают в однопанельном режиме: список → Enter → подробности → Esc.
- Разрушительные действия (`rm`, перезапись) требуют подтверждения.
- Поддержка мыши в v1 не требуется.

### 6.3 Буфер обмена по SSH

- Основной способ: OSC 52 (`ESC ] 52 ; c ; <base64> BEL`). tmux и screen на стороне клиента обрабатывают OSC 52 сами (tmux нужен `set-clipboard on`). passh оборачивает последовательность для tmux или screen только в административном режиме, когда на сервере задан `$TMUX` или `$STY`.
- Очистка: по истечении тайм-аута passh отправляет OSC 52 с пустым содержимым, но только если сессия ещё жива (ограничения R6). Неинтерактивный `copy` остаётся подключённым в течение `clipboard.clear_after`, затем очищает буфер и завершается.
- `passh doctor` отправляет тестовую строку, а затем очистку, чтобы пользователь мог убедиться, что его терминал поддерживает и то и другое (установку поддерживают iTerm2, kitty, WezTerm, Windows Terminal, Alacritty и tmux с `set-clipboard on`; в Termux нужно включить настройку OSC 52).
- Запасной вариант: если OSC 52 не поддерживается или отключён (`clipboard.osc52 = false`), `copy` завершается ошибкой с подсказкой (`show --field password | pbcopy`). Секрет не выводится в историю прокрутки терминала.
- История буфера обмена на клиенте (Universal Clipboard в macOS, история буфера обмена Android, менеджеры буфера обмена) может сохранять копии. README советует исключить приложение терминала из этих инструментов.

### 6.4 Неинтерактивные команды по SSH

При `ForceCommand` sshd игнорирует команду, которую ввёл клиент, и передаёт её в `SSH_ORIGINAL_COMMAND`. passh:

1. Определяет ключ: читает `$SSH_USER_AUTH`, требует ровно одну строку `publickey`, вычисляет её отпечаток SHA256 и загружает политику этого ключа из `policy.toml` (§3.3). Неизвестный ключ, отсутствующая переменная или некорректный файл → отказ и запись в журнал.
2. Если `SSH_ORIGINAL_COMMAND` пуст, запускает TUI (нужен PTY; без него выводит справку по использованию).
3. Иначе разбивает команду собственным парсером passh: слова разделяются пробелами, одинарные или двойные кавычки служат для группировки. Вне кавычек символы ``; | & $ ` < > ( ) { } [ ] * ? ~ # \ !`` отклоняются, потому что пользователь, скорее всего, ожидал поведения shell; shell же не запускается никогда. Внутри кавычек допускается любой символ, разрешённый правилами для путей. Управляющие символы отклоняются всегда.
4. Принимает только команды и флаги, разрешённые для этого ключа по §6.1. Первым словом может быть `passh`, а может и не быть. **Глобальные флаги (`--admin` и всё, что изменило бы режим или политику) из `SSH_ORIGINAL_COMMAND` не принимаются никогда.**
5. Пишет в журнал systemd (родной протокол journal, без дополнительного бинарного файла): имя и отпечаток ключа, имя команды и путь, но никогда не значения. Отклонённые команды тоже записываются.

Пример с клиента, у ключа которого `batch = true`: `ssh vault@pi show work/github --field password | pbcopy`. Для этого ключ уже должен быть разблокирован интерактивной сессией (§5.1). Пути с символами shell нужно заключать во внутренние кавычки, потому что shell клиента снимает внешние: `ssh vault@pi "show 'work/a&b'"`.

## 7. Экспорт и печать

### 7.1 Экспорт

```
passh export --format <archive|json|csv|bitwarden-json> [--tag t] [--folder f]
             [--to <name> | --confirm-plaintext] [--spreadsheet-safe] [-o file]
```

| Формат | Содержимое | Зашифрован | Применение |
|---|---|---|---|
| `archive` (по умолчанию) | `tar.gz` всего репозитория **включая `.git`**: записи, подписи, `.passh/` (с обёрнутым ключом) и манифест | Да, записи остаются зашифрованными GPG | Резервное копирование, переезд на другой хост. Импортируется как клон: проверяется перед использованием (§8.4) |
| `json` | Собственная схема passh (§7.3) | С `--to` | Скрипты, миграция |
| `csv` | `folder,name,username,password,url,tags,notes`, кавычки по RFC 4180 | С `--to` | Импорт в KeePassXC и другие менеджеры |
| `bitwarden-json` | Схема незашифрованного экспорта Bitwarden | С `--to` | Миграция на Vaultwarden/Bitwarden |

Правила:

- **Данные экспорта никогда не выводятся в терминал.** Перенаправляйте stdout и используйте `ssh` **без `-t`**: PTY смешивает stderr с потоком и превращает LF в CRLF, и файлы портятся. Запросы никогда не выводятся в stdout.
- **Права в зависимости от значения `export` у ключа (§3.3):**
  - `none`: ничего;
  - `encrypted`: `archive`, а также другие форматы с `--to`;
  - `plaintext`: дополнительно открытый текст с `--confirm-plaintext`.
  - Административному режиму доступно всё.
- **`--to <name>`** шифрует для получателя, закреплённого в `pins.toml` (`[export.recipients]`, получатель age или отпечаток GPG; записывается только в административном режиме). Произвольные получатели не принимаются: иначе украденный SSH-ключ мог бы экспортировать данные на собственный ключ, а это равносильно открытому тексту. Пример: `ssh vault@pi export --format bitwarden-json --to laptop > vault.json.age`.
- **Открытый текст по SSH:** ключ с `export = "plaintext"` плюс `--confirm-plaintext`. Выдавайте это право только устройству, которому доверили бы всё хранилище целиком (§9).
- **Административный режим с `-o file`:** для открытого текста пользователь должен ввести `EXPORT PLAINTEXT` в `/dev/tty`. Файл создаётся с правами 0600 на tmpfs (проверяется через `statfs`); другие расположения отклоняются, если не указан `--allow-disk`.
- Все форматы, кроме `archive`, расшифровывают записи, поэтому им нужен разблокированный агент, а при выводе в конвейер — ещё и `batch` у ключа.
- **Значения CSV по умолчанию выводятся без изменений**, потому что файл предназначен для менеджера паролей. `--spreadsheet-safe` добавляет `'` в начало ячеек, которые начинаются с `= + - @`, табуляции или CR, чтобы предотвратить внедрение формул при открытии файла в электронной таблице. passh предупреждает, что это меняет значения, включая пароли, поэтому такой файл нельзя импортировать в менеджер паролей.
- Каждый экспорт записывается в журнал (ключ, формат, фильтры, но никогда не значения).

### 7.2 Печать

Цель — бумажный аварийный лист, который переживёт потерю сервера и его резервных копий.

```
passh print [--tag t] [--folder f] [--fields password,username,url] [--format pdf|txt] [--confirm-plaintext]
passh --admin print --recovery-kit [--with-key]
```

- **Лист паролей — это вывод открытого текста.** Он подчиняется правилам экспорта открытого текста (§7.1): ключ с `export = "plaintext"` и `--confirm-plaintext` или административный режим. Вывод идёт только в stdout и никогда в терминал — печатать предполагается на клиенте. Если на сервере настроен CUPS, `--lp <printer>` отправляет задание напрямую (только в административном режиме).
- `pdf`: генерируется на чистом Go (`go-pdf/fpdf`, без cgo) со встроенным моноширинным шрифтом TTF с поддержкой UTF-8 (например, DejaVu Sans Mono), поэтому нелатинские символы печатаются правильно. A4/Letter, группировка по папкам, пароли моноширинным шрифтом с пометкой неоднозначных символов (`0/O`, `1/l/I`), дата печати в нижнем колонтитуле и «CONFIDENTIAL» на каждой странице.
- `txt`: постраничная моноширинная разметка для `lp` или быстрого просмотра.
- **`--recovery-kit`** — **только в административном режиме**. Печатает отпечаток ключа, URL резервных репозиториев и шаги восстановления (§8.4–8.5). **Никаких паролей.**
  - `--with-key` добавляет `.passh/secret-key.asc.age` в виде текста и QR-кодов (для больших ключей RSA их несколько). Основной способ вернуть ключ — сканирование; ручной ввод — крайняя мера. Эта вторая копия нужна на случай, если копия в резервной копии повреждена. Она по-прежнему защищена парольной фразой.
  - Прямо на странице набора написано: **парольной фразы на этом листе нет**; храните её отдельно (в памяти или в другом физическом месте).
- Клиентам следует распечатать файл, а затем удалить его; README отмечает, что PDF, забытые в Downloads, — это утечка.

### 7.3 Схема JSON (собственная)

```json
{

  "exported_at": "2026-11-15T12:00:00Z",
  "entries": [
    {
      "path": "work/github",
      "password": "…",

```

При импорте (в будущем) каждый `path` проходит правила для путей (§4.6), а каждое значение перед показом — очистку по R8.

### 7.4 Страница печати (веб)

Одноразовая HTTPS-страница с листом паролей. Вы открываете её в браузере в LAN или VPN и печатаете, нигде не сохраняя файл.

**Запуск**

- Запускается из TUI клавишей `P` или командой `passh print --web [--tag t] [--folder f] [--fields …]`.
- Только в интерактивной сессии (с PTY), при разблокированном и проверенном хранилище (§4.5).
- Права: `print_web.enabled = true` в `policy.toml` (§3.3), плюс ключ с `export = "plaintext"` либо консольный или административный режим.
- Для подтверждения пользователь вводит `PRINT`.
- Затем passh показывает с обратным отсчётом:
  - URL для каждого привязанного адреса и его QR-код для телефонов;
  - отпечаток сертификата.

  `c` копирует URL в буфер обмена клиента (OSC 52).
- На хосте одновременно может работать только одна страница печати. Сервер работает внутри процесса passh, а не как демон.

**Сеть**

- Слушает только на адресах из `print_web.interfaces` и только на **частных** адресах: RFC 1918, `100.64.0.0/10` (Tailscale) и IPv6 ULA `fc00::/7`.
  - Публичный адрес отклоняется, поэтому на VPS используется только VPN.
  - Никогда не привязывается к `0.0.0.0` или `::`.
- Соединения с адресов вне `allow_from` закрываются до TLS. По умолчанию это подсети привязанных адресов.
- Заголовок `Host` должен совпадать с одним из привязанных адресов или с одним из `hostnames`. Это защищает от DNS rebinding.
- Только HTTPS, TLS 1.3. LAN, в отличие от VPN, не шифруется, поэтому обычный HTTP не предлагается никогда.

**Сертификат**

- **Локальный CA.** Его создаёт `passh --admin print-web init` (ECDSA P-256).
  - Критическое расширение X.509 **name constraints** (ограничения имён) разрешает ему только настроенные частные подсети и `hostnames`. Даже с украденным ключом CA нельзя выдать себя за любой другой сайт.
  - Его ключ хранится в `~/.config/passh/print-ca.key` (0600). `doctor` заранее предупреждает об истечении срока действия CA.
- **Установка.** `passh --admin print-web ca` выводит сертификат CA и его отпечаток. Установите его на устройства, с которых печатаете; в README есть инструкции для macOS, Windows, iOS и Android.
- **Сертификат на каждый запуск.** При каждом запуске выпускается конечный (leaf) сертификат для привязанных адресов и `hostnames`, действительный в течение TTL плюс одна минута. Его ключ генерируется в памяти и никогда не записывается.
- **Если CA не установлен,** браузер показывает предупреждение, а TUI — отпечаток конечного сертификата для сверки. Если в LAN проигнорировать предупреждение, вы становитесь уязвимы для активного атакующего в этой LAN (§9).

**Токен и время жизни**

- URL имеет вид `https://<address>:<port>/p/<token>`, токен — 128-битный случайный (`crypto/rand`, base64url).
- **Страница отдаётся один раз.** Первый `GET` с правильным токеном расходует его, и сервер останавливается, как только ответ записан. Другие методы получают 405, и токен при этом не расходуется.
- Кроме того, сервер останавливается при первом из событий:
  - истёк `print_web.ttl`, по умолчанию 5 мин, максимум 15;
  - любая блокировка (§5.2), включая блокировку из другой сессии, которую обнаруживает проверка агента каждые 5 с;
  - завершение TUI или команды либо окончание сессии;
  - `Esc` в диалоге печати;
  - 5 запросов к `/p/` с неверным токеном; они записываются в журнал как возможное сканирование. Запросы к другим путям, например `/favicon.ico`, получают 404 и не учитываются.
- Предпросмотр ссылок и предварительная загрузка в браузере могут израсходовать токен раньше. Тогда пользователь увидит «already used» и начнёт заново. README предупреждает, что URL нельзя вставлять в чаты.

**Страница**

- То же содержимое и та же разметка, что и у листа PDF (§7.2): группировка по папкам, только выбранные поля, пометка неоднозначных символов, дата печати и «CONFIDENTIAL». CSS для печати на A4/Letter с разрывами страниц между папками.
- Никакого JavaScript, внешних шрифтов и изображений. Пользователь печатает через Ctrl/Cmd+P.
- Записи расшифровываются при поступлении запроса, по одной: отрисовываются, передаются потоком и затираются. Действуют ограничения R3.
- Каждое значение проходит экранирование `html/template` плюс экранирования R8, поэтому содержимое записи не может внедрить HTML.
- Заголовки ответа:
  ```
  Cache-Control: no-store
  Content-Security-Policy: default-src 'none'; style-src 'sha256-…'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
  Referrer-Policy: no-referrer
  X-Content-Type-Options: nosniff
  Cross-Origin-Opener-Policy: same-origin
  ```
  CSP блокирует скрипты и любые исходящие запросы. Даже если экранирование не сработает, страница не сможет никуда отправить пароли.
- **Журналирование:** запуск (ключ, фильтры, адреса), загрузка страницы (адрес клиента) и остановка с указанием причины. Никогда не значения.
- **После печати** закройте вкладку. Браузер может хранить страницу в памяти и в данных восстановления сессии, а «Сохранить как PDF» или очередь печати могут оставить файлы на клиенте. Это описано в README.

## 8. Резервное копирование и восстановление

### 8.1 Что резервируется

| Что | Как | Периодичность |
|---|---|---|
| Хранилище: зашифрованные записи, подписанная история, закрепления, открытый ключ, обёрнутый секретный ключ | Каждое изменение — подписанный коммит. После каждого коммита passh выполняет push в `backup.remotes` (§8.3) | При изменении |
| Снимок хранилища | `passh export --format archive` или restic для `~/.password-store` (пример таймера systemd есть в README, не встроен) | Ежедневно |
| Набор для восстановления (бумажный) | `passh --admin print --recovery-kit [--with-key]`, хранится офлайн | Один раз и при смене ключа |

**Для восстановления достаточно резервной копии и парольной фразы.** Это осознанный выбор (ADR-8): любой, у кого есть резервная копия, может попытаться подобрать парольную фразу офлайн. Раздел 8.2 делает такой подбор настолько дорогим, насколько это практически возможно.

### 8.2 Встроенный секретный ключ

- **`.passh/secret-key.asc.age`** хранит секретный ключ в двух слоях:
  - внутренний: вывод `gpg --export-secret-keys --armor <fpr>`, который остаётся защищён парольной фразой ключа (OpenPGP S2K);
  - внешний: шифрование age по парольной фразе (`filippo.io/age`, scrypt, коэффициент сложности ≥ 2¹⁸, около 256 МиБ памяти на одну попытку).

  Оба слоя используют **одну и ту же парольную фразу**. scrypt требователен к памяти (memory-hard), поэтому подбор на GPU идёт гораздо медленнее, чем против одного OpenPGP S2K.
- **`.passh/pubkey.asc`** хранит открытый ключ. При восстановлении его отпечаток сверяется с тем, который вводит пользователь.
- **Создание:** `init`, `init --adopt` и `passh --admin key backup` создают оба файла. Для экспорта gpg запрашивает парольную фразу через pinentry. Затем passh дважды запрашивает её в `/dev/tty` для слоя age, держит в защищённой памяти (R3) и затирает. passh не может проверить, что эти две фразы совпадают, и прямо об этом сообщает.
- **Стойкость парольной фразы.** Безопасность каждой резервной копии равна стойкости парольной фразы:
  - `init` предлагает сгенерированную парольную фразу из 6 слов (большой словарь EFF, `crypto/rand`, около 77 бит; R9);
  - для слоя age самостоятельно выбранная парольная фраза короче 20 символов отклоняется;
  - README объясняет этот компромисс.
- **После смены парольной фразы** (`gpg --passwd`) выполните `passh --admin key backup`. Старые обёрнутые копии остаются в истории git и в репозитории только на добавление (append-only), по-прежнему защищённые **старой** парольной фразой. Поэтому смена слабой или утёкшей парольной фразы не защищает уже существующие резервные копии; в таком случае создайте новый ключ через `recipients set`. `doctor` напоминает об этом, если `pubkey.asc` и связка ключей расходятся.

### 8.3 Резервный репозиторий

- **Настройка:** `passh --admin remote add <name> <ssh-url>`:
  1. проверяет URL (§5.5);
  2. создаёт ключ для push `~/.ssh/passh_backup` (ed25519), если его нет, и выводит его открытый ключ, который нужно зарегистрировать в удалённом репозитории как deploy key с правом записи;
  3. один раз подключается, показывает отпечаток ключа хоста удалённого репозитория для подтверждения и закрепляет его в `<state>/known_hosts`;
  4. записывает репозиторий в `backup.remotes` подписанным коммитом.

  `remote list` показывает каждый удалённый репозиторий и время его последнего push; `remote remove` удаляет один из них.
- **Только push.** passh никогда не выполняет pull или fetch из резервного репозитория. `sync` = проверка (§4.5), затем push. Содержимое удалённого репозитория читает только `restore`, и только на новом хосте.
- **Когда:** после каждого коммита passh синхронно выполняет push с тайм-аутом 10 с. Результат записывается в каталог состояния и отображается в заголовке TUI и в `doctor` («last push 3 days ago ⚠»). `sync` повторяет попытку.
- **Только на добавление (append-only):** удалённый репозиторий отклоняет force-push и удаление веток (например, `receive.denyNonFastForwards = true`, `receive.denyDeletes = true` в bare-репозитории или защита веток на git-хостинге). Это защищает от скомпрометированного **сервера**, который переписывает резервные копии. От скомпрометированного **удалённого репозитория** это не защищает (§9).
- **Доступ:**
  - ключ push на сервере имеет право записи только в этот один репозиторий;
  - ключ хоста удалённого репозитория закреплён в `<state>/known_hosts`;
  - удалённый репозиторий хранит обёрнутый секретный ключ, поэтому он должен быть закрытым.
- **Дополнительно:** вторая машина зеркалирует резервный репозиторий, забирая данные из него, а не с Pi. Так появляется копия, в которую Pi не может писать.

### 8.4 Восстановление

Это также тест приёмки.

1. Установите бинарный файл на чистый хост и настройте пользователя `vault` и sshd (§3).
2. Выполните `passh --admin restore <remote-url | archive> --fingerprint <fpr>`. Отпечаток берётся из набора для восстановления или из ваших записей, но никогда не из склонированного репозитория. Затем passh:
   1. клонирует с `--no-checkout` и усиленными настройками git (§5.5) или так же распаковывает архив. Для ssh-адреса сначала настраивает доступ так же, как `remote add` (§8.3): использует `~/.ssh/passh_backup` или создаёт его и выводит открытый ключ, который нужно зарегистрировать в удалённом репозитории (для восстановления достаточно доступа на чтение), а также подтверждает и закрепляет ключ хоста удалённого репозитория;
   2. проверяет, что у `.passh/pubkey.asc` указанный отпечаток, и импортирует его;
   3. проверяет, что HEAD подписан этим ключом и что `.gpg-id` и `.gpg-id.sig` корректны (§4.4, §4.5). Любая ошибка останавливает восстановление, и passh перечисляет проблемы;
   4. показывает дату вершинного коммита и число записей для подтверждения. Удалённый репозиторий может отдать более старое, но корректно подписанное состояние (откат, §9);
   5. запрашивает парольную фразу, разворачивает `.passh/secret-key.asc.age`, импортирует ключ в gpg и устанавливает ему ownertrust ultimate, чтобы работал и обычный `pass`;
   6. выполняет checkout, записывает `pins.toml`, `verified-head` и `gpg-agent.conf`, затем запускает `reindex`.
3. `passh show` работает.

**Из резервной копии папки** (§3.5): верните `backup/` на место, запустите контейнер с пустой `local/` и выполните `passh --admin restore --in-place --fingerprint <fpr>`. Команда выполняет проверки 2–6 для существующего `~/.password-store` вместо клонирования. Она также настраивает доступ к удалённому репозиторию, как в шаге 2.1, поэтому выведенный ключ push нужно снова зарегистрировать в удалённом репозитории.

### 8.5 Аварийное восстановление без passh

Хранилищем можно пользоваться и стандартными инструментами:

```bash
git clone <backup-remote> ~/.password-store
age -d ~/.password-store/.passh/secret-key.asc.age | gpg --import   # passphrase for age, then for gpg
gpg --import-ownertrust <<< "<FPR>:6:"
pass show bank/revolut              # or: gpg -d ~/.password-store/bank/revolut.gpg
```

Этот путь пропускает проверку подписей. README рекомендует предпочитать `passh restore`, когда важна целостность резервной копии.

### 10.3 Ключевые интерфейсы

```go
type Crypto interface {
    Decrypt(ctx context.Context, path paths.Safe) (*secmem.Buffer, error)
    Encrypt(ctx context.Context, plaintext *secmem.Buffer) ([]byte, error) // recipients from verified pins only
    SignDetached(ctx context.Context, data []byte) ([]byte, error)
    VerifyDetached(ctx context.Context, data, sig []byte) (Signer, error)  // Signer = primary-key fingerprint + status
    Unlock(ctx context.Context) error             // primes decryption and signing keys (§5.1)
    IsUnlocked(ctx context.Context) (bool, error) // probe agent (KEYINFO), never prompts
    Lock(ctx context.Context) error               // flush agent cache
}

type Store interface {
    List(prefix paths.Safe) ([]paths.Safe, error)
    Read(path paths.Safe) (*entry.Entry, error)
    Write(path paths.Safe, e *entry.Entry) error // lock → verify → pins → encrypt → write → index → signed commit
    Move(src, dst paths.Safe) error
    Remove(path paths.Safe) error
}

type Policy interface {
    Key() KeyInfo                         // name, fingerprint, access, batch, export, fresh_unlock
    Allow(cmd Command, interactive bool) error
}
```

`paths.Safe` может создать только валидатор, поэтому непроверенные пути не могут попасть ни в хранилище, ни в подпроцессы.

## 11. Архитектурные решения

**ADR-1: Системный `gpg` вместо нативной реализации OpenPGP на Go**
- *Решение:* вызывать внешний `gpg` для расшифровки, шифрования, подписи и проверки подписи.
- *Почему:* совместимость с существующими хранилищами и ключами pass; gpg-agent обеспечивает кеширование парольной фразы, pinentry и будущую поддержку YubiKey; не нужно разбирать формат, в котором GnuPG хранит закрытые ключи.
- *Цена:* зависимость от `gnupg` во время выполнения; кеш общий для пользователя, а не для процесса (§5.2); конфигурация агента доступна на запись пользователю `vault` (§9); разбор вывода должен быть строгим (§5.5).
- *Альтернатива, которая остаётся открытой:* бэкенд **age** (`filippo.io/age`, как в gopass) через интерфейс `Crypto`. Он дал бы бинарный файл без внешних зависимостей, кеш внутри процесса для каждой сессии и никакой поверхности атаки через конфигурацию агента, но сломал бы совместимость с pass. age уже используется как зависимость — для экспорта и обёртки ключа.

**ADR-2: Папки остаются основными; теги — дополнение с зашифрованным индексом** (§4.3)

**ADR-3: Расшифровка на сервере (модель A)**: никакой настройки на клиентах ценой риска, описанного в §9.

**ADR-4: Ограниченный режим по умолчанию.** Никакого внешнего редактора, пейджера и проброса команд в git, потому что каждый из них — известный путь выхода в shell (§5.4, §6.1). Административный режим включается явно и по SSH запрещён (§3.4).

**ADR-5: Подписанная история.** Целостность обеспечивают подписанные коммиты и подписанный `.gpg-id`, потому что одно шифрование GPG не подтверждает, кто автор изменений. Подписанная вершина ручается за своих предков, поэтому принятие и подтверждение оформляются подписанными коммитами, которые попадают в резервную копию (§4.4, §4.5).

**ADR-6: Права для каждого ключа — от sshd, а не через `command=` в `authorized_keys`.** `ForceCommand` переопределяет `command=`, поэтому параметры отдельных ключей там никогда не действуют. `ExposeAuthInfo` сообщает passh, каким ключом прошла аутентификация; принадлежащий root `policy.toml` сопоставляет этот ключ с правами (§3.3). `ForceCommand` остаётся единственной контрольной точкой.

**ADR-7: Резервные копии только через push.** Удалённые репозитории служат только для резервного копирования, поэтому сервер никогда не делает из них fetch. Это убирает основной путь, по которому могло бы прийти недоверенное содержимое git. Содержимое удалённого репозитория читает только `restore`, и он выполняет проверку до checkout (§8.3, §8.4).

**ADR-8: Секретный ключ входит в резервную копию.** Решение владельца: резервной копии и парольной фразы должно хватать для восстановления где угодно. Компромисс: любой, у кого есть резервная копия, может подбирать парольную фразу офлайн. Меры защиты: внешний слой age scrypt, сгенерированная парольная фраза из 6 слов, которую предлагает `init`, минимум 20 символов для слоя age и документация (§8.2, §9).

**ADR-9: Одноразовая страница печати по HTTPS в LAN и VPN.** Решение владельца: печатать из любого браузера без сохранения файла. Компромисс: лист с открытым текстом передаётся по сети. Поэтому страница по умолчанию выключена, требует права на экспорт открытого текста, привязывается только к частным адресам, использует TLS с локальным CA с ограничениями имён, отдаётся один раз по случайному токену и останавливается через 5 минут или при блокировке (§7.4, §9).

## 13. Критерии приёмки (v1)

### 13.1 Функциональные

1. Бинарный файл устанавливается на новый Raspberry Pi одной командой; `passh doctor` весь зелёный.
2. Существующий `~/.password-store` принимается через `init --adopt`, после чего `pass` по-прежнему с ним работает.
3. `ssh vault@pi` открывает TUI; один запрос парольной фразы на сессию, включая первую запись.
4. После простоя в течение `session.idle_ttl` или после отключения следующая расшифровка снова запрашивает парольную фразу.
5. Копирование из TUI попадает в буфер обмена клиента, а через 30 с отправляется очистка.
6. Экспорт в Bitwarden JSON импортируется в Vaultwarden; CSV импортируется в KeePassXC, и пароли, начинающиеся с `= + - @`, не искажаются.
7. `passh restore`, когда есть только резервный репозиторий и парольная фраза, работает на новом хосте — для хранилища, созданного passh, для принятого хранилища и для хранилища после `recipients set`.
8. Аварийное восстановление без passh (§8.5) работает только с `git`, `age`, `gpg` и `pass`.
9. Страница печати, запущенная из TUI, открывается без предупреждения о сертификате на ноутбуке с установленным CA — и через LAN, и через VPN. Она печатается, а сервер после загрузки останавливается.
10. Развёртывание в Docker (§3.5) проходит `doctor`. На новом хосте для восстановления через `restore --in-place` достаточно одной копии `backup/` и парольной фразы.

### 13.2 Тесты безопасности (по возможности автоматизированные)

1. Правила для путей: `..`, абсолютные пути, ведущий `-` или `.` в любом сегменте, управляющие символы и символы Cf, а также символические ссылки отклоняются. Символическая ссылка, закоммиченная в git, извлекается как обычный файл.
2. Изменённый `.gpg-id`, файл с недействительной подписью или вложенный `work/.gpg-id` блокируют любую запись.
3. Неподписанный HEAD обнаруживается при запуске и при восстановлении и блокирует запись. После `verify --accept` новое восстановление этой истории проходит успешно.
4. Незакоммиченное изменение записи или неотслеживаемый файл обнаруживаются и блокируют запись.
5. Переписанная история (`verified-head` не является предком HEAD) обнаруживается.
6. `.git/config` с `gpg.program`, `core.sshCommand`, `filter.*`, `include.path` или неизвестным ключом `diff.*` отклоняется при запуске, и ничего не выполняется.
7. Поддельные строки `[GNUPG:]` в открытом тексте записи или в stderr gpg ни на что не влияют. Незашифрованная или только подписанная «запись» отклоняется.
8. `gpg.conf` с `encrypt-to <other key>` не добавляет получателя (шифротекст проверяется через `gpg --list-only`).
9. После любой команды на постоянном диске нет файлов с открытым текстом (тест сравнения состояния файловой системы, выполняется с отключённым swap).
10. Escape-последовательности (включая OSC 52) и символы bidi в содержимом записей, сообщениях коммитов и путях отображаются безвредно: в TUI, в `show` в терминале, в `show` через конвейер, в `log` и в выводе ошибок.
11. Сгенерированные пароли проходят тест равномерности по критерию хи-квадрат на 10⁶ выборках.
12. Сквозной тест с настоящим sshd (в контейнере): шаблон проходит `sshd -t`. Ключ телефона получает права только на чтение, а неизвестный ключ отклоняется. Значения `SSH_ORIGINAL_COMMAND` с ``; | & $ ` > <`` вне кавычек, с неизвестными командами или флагами либо с `--admin` отклоняются, и ничего не запускается.
13. Обход дерева cobra показывает, что каждая команда и каждый флаг есть в матрице §6.1. С ключом только для чтения отклоняется любая запись; без `batch` отклоняется любое неинтерактивное чтение.
14. В режиме SSH passh напрямую запускает только `gpg`, `gpg-connect-agent` и `git` (тестовые хуки в `internal/exec`), а git запускает `ssh` только через закреплённый `GIT_SSH_COMMAND`.
15. Если в `gpg-agent.conf` TTL больше настроенных, нет строк TTL, нет `no-allow-loopback-pinentry` или `pinentry-program` указывает не на системный pinentry, passh отказывается расшифровывать.
16. Неинтерактивная команда при заблокированном ключе сразу завершается ошибкой, и pinentry нигде не запускается, в том числе для подписи.
17. Экспорт: вывод в терминал отклоняется. Открытый текст без соответствующего права у ключа или без `--confirm-plaintext` отклоняется. `--to` с незакреплённым получателем отклоняется. Экспортированный файл не содержит текста запросов.
18. `--admin` отклоняется, если задана любая переменная `SSH_*` или stdin не является TTY.
19. Оба из двух параллельных писателей успешно добавляют свои коммиты, и индекс остаётся согласованным. При SIGPIPE (`show … | head -c1`), SIGHUP и SIGTERM секреты затираются, временные каталоги удаляются, а кеш агента сбрасывается там, где это предписывает §5.2.
20. Три неудачные разблокировки включают задержку, которая действует во всех сессиях и записывается в журнал.
21. Страница печати отклоняется для ключа без `export = "plaintext"`, без PTY, при `print_web.enabled = false` и на интерфейсе, у которого есть только публичные адреса.
22. Страница печати отдаётся один раз по TLS. Повторная загрузка, неверный заголовок `Host` и клиент вне `allow_from` получают отказ; 5 неверных токенов останавливают сервер. Сервер останавливается по истечении TTL, при блокировке (включая блокировку из другой сессии) и по SIGHUP.
23. Содержимое записи с `<script>`, `<img src=…>` или `</style>` отображается на странице печати как текст. Заголовки ответа соответствуют §7.4, а headless-браузер, загружающий страницу, не делает ни одного исходящего запроса.
24. Chrome, Firefox и Safari отклоняют конечный сертификат, выпущенный CA страницы печати для имени вне его ограничений.
25. В контейнере passh отказывается расшифровывать, если cgroup разрешает swap, а на хосте есть swap на диске. Контейнер работает с корневой файловой системой только для чтения и только с возможностями из §3.5, а в `backup/` нет ни одного закрытого ключа без защиты парольной фразой.

## 14. Открытые вопросы

1. TOTP (поле `otp:` + `passh otp <path>`) в v1 или в v1.1?
2. Сделать ли индекс тегов необязательным для тех, кто не хочет никаких лишних файлов в хранилище?
3. Должна ли политика ключа также ограничивать его подмножеством папок или тегов (например, `folders = ["work"]` в `policy.toml`)? Механизм для этого уже есть; входит ли это в v1?
4. Стоит ли будущий бэкенд age потери совместимости с pass, учитывая, что он убирает поверхность атаки через конфигурацию агента?
5. Использовать ли для подписи отдельный подключ подписи на аппаратном токене (YubiKey), чтобы скомпрометированный сервер не мог подписывать без физического касания?

Решено в v0.3: механизм прав для каждого ключа (ADR-6), модель синхронизации (ADR-7), путь административного доступа (§3.4), модель резервного копирования ключа (ADR-8), обработка ключей подписи с истёкшим сроком действия (§4.5), поведение CSV по умолчанию (§7.1), строгость правил для путей (§4.6), отзыв доступа после смены ключа (§4.4).
